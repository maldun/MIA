## Phase 4: expressions

- `godot/expression_engine.gd` (`ExpressionEngine`): the central API. `play(name, duration)` / `apply_preset(dict, duration)`
  blend smoothly (default 0.25 s, easing `smooth|linear|sine|cubic`), keys not in the new preset go back to 0,
  automatic blinking (2.5-6 s apart, suppressed while the eyes are closed), subtle idle motion (breathing, head sway).
  `validate()` rejects unknown shape keys / bone params, clamps values and logs every correction.
- Presets: `godot/presets/library.json`, `{"presets": [ {name, description, weights, bones, tags, source} ]}`.
  The 14 required ones: greet, no, annoyed, talk, yes, idle (from `expressions.json`) and neutral, happy, sad, angry,
  surprised, embarrassed, smug, thinking. Bone params (degrees): head_pitch (+ down), head_yaw (+ viewer's right),
  head_roll, eye_pitch, eye_yaw.
- Tests: `godot --headless --path ui/godot --script res://tools/test_expressions.gd` (checks validation, blending, blinking, idle).
- Review: `godot/tools/contact_sheet.gd` + `tools/montage.py` render all presets into one image;
  the web page has a collapsible button bar to play them (temporary, replaced by the editor in phase 6).

### Gestures, camera and the eye fix (after phase 4)

- `godot/gesture_engine.gd` + `presets/gestures.json`: relaxed arms by default, 12 gestures; a preset can start one (`"gesture"`).
  Preview all poses with `godot/tools/gesture_sheet.gd`.
- Default camera shows the whole figure; the menu (collapsed at start) has camera views body/bust/face, all expressions and gestures.

### HTTPS for other devices

Godot's web export (audio worklet, WebGL) needs a secure context. `http://localhost` is one, `http://<lan address>` is not:
other computers and phones get a message that HTTPS is needed. `tools/https_proxy.sh <https port> <target host:port>`
runs a TLS proxy (openssl + socat, self-signed certificate in `ui/certs`):

- `ui/tools/https_proxy.sh 8586 <lan address>:8585` for MIA's page (and `"https_port":8586` in `setup_cfg.json`),
- `ui/tools/https_proxy.sh 8443 127.0.0.1:8060` for the character test server (`tools/serve_web.py`).

The chat page connects to the socket of the address it was loaded from, so the same page works on localhost, in the LAN and over HTTPS.
`python ui/tools/browser_check.py https://<address>:8586/ out.png --insecure` checks a page in headless Chromium.

## Phase 6: expression editor and preset API

- **Backend:** the preset API is part of MIA's Flask app (`presets_api.py`, storage in `preset_store.py`), not a second FastAPI server:
  the page, the character and the presets come from one server with one set of access rules (HTTPS proxy, allowed origins, token).
  One json file per preset in `presets_dir` (default `data/presets`, git-ignored), filled from `godot/presets/library.json` on first use.
  REST: `GET /api/presets` (all + version + `token_required` + protected names), `GET /api/presets/version`, `GET /api/presets/<name>`,
  `POST /api/presets`, `PUT /api/presets/<name>` (a different name in the body renames), `DELETE /api/presets/<name>` (409 for presets
  MIA's emotions use, `?force=1` overrides), `GET /api/shape-keys`, `GET /api/gestures`.
  Values are corrected like in the character (unknown shape keys, bones and gestures removed, values clamped) and reported as `corrections`.
- **Safety:** writing needs `Content-Type: application/json` (no cross-site form posts), a known origin if the browser sends one
  (the page's own address is always fine), and the header `X-MIA-Token`. The token is created on the first start (`data/editor_token.txt`, mode 600, not in version control, printed at start); `editor_token` in the configuration overrides it, `""` switches it off. Desktop clients (tests) read it from `MIA_TOKEN` or the file `MIA_TOKEN_FILE`. Names are 1-40 letters, digits, `-`, `_`
  (no paths), files are written atomically, bodies over 64 KB are refused.
- **Character:** `godot/preset_api.gd` (client, polls the version every 10 s so other devices' changes show up; offline it keeps the
  bundled presets), `godot/expression_editor.gd` (the panel: right side on wide screens, bottom sheet on phones, big slider handles,
  solid background), `godot/presets/shape_keys.json` (categories and descriptions of the 57 shape keys, also used for validation and,
  later, for the LLM prompt). `?editor` opens the editor at start, the dev menu has an "Expression editor" button.
  The stretch aspect is `expand` now: the canvas fills any window (no black bars next to the character).
- **Tests:** `python tests/test_presets_api.py` (23 tests: storage, rules, API, token, origin),
  `godot --headless ... --script res://tools/test_editor.gd` (43 checks with an in-memory server),
  `MIA_URL=http://127.0.0.1:8685 godot ... --script res://tools/test_editor_live.gd` (real HTTP against a running MIA app and a second client
  as "another device"), `tools/editor_shot.gd` renders the editor to a PNG (wide and phone shapes).

## Chat backend, phase C2

The server now describes the conversation as **messages** (`chat_service.py`, `chat_log.py`, `chat_api.py`, `moods.py`).
`chat_send` is answered immediately; the exchange runs in a background task (one at a time, one more may wait), so the socket
handler never blocks. The old events (`message`, `answer`, `audio_reload`, ...) still work for the page of C1 and are removed in C3.

| Direction | Event | Payload |
|---|---|---|
| page -> server | `chat_send` | `{id, text}`, acknowledgement `{ok, message, queued, command}` or `{ok: false, error}` |
| page -> server | `chat_stop` | acknowledgement `{stopped}`; the text received so far stays, the message is marked `stopped` |
| server -> all | `chat_message` | a complete message: yours, system notes (commands), automatic MIA messages (`auto: true`, e.g. the hourly time check) |
| server -> all | `chat_start` / `chat_delta` / `chat_done` | MIA's answer: start, cumulative text (at most about 20 per second), final `{id, text, emotion, status}` |
| server -> all | `chat_status` | `{busy, activity, model, profile, queue, mood: {emotion, emoji, text, since, activity}}`, also sent on connect |
| server -> all | `chat_error` | `{id?, message}` |

REST: `GET /api/chat/history?before=<id>&limit=50`, `GET /api/chat/status`, `GET /api/chat/commands`,
`POST /api/chat/clear {"scope": "log"}` (header `X-MIA-Token`, the editor token unless `chat_token` is set).

- **Mood line:** `moods.json` (edit it; read again when it changes) holds first person phrases per emotion keyword and per activity
  (thinking, dreaming, offline ...). The phrase is chosen on the server, never the same twice in a row, and sent to every device;
  a mood returns to "Ready when you are." after `mood_hold_minutes`.
- **Not in the chat log:** calibration, the hourly prompt to the model, summaries and penalties (the reminder to start with an emotion).
- **Stop:** `Communicator.exchange(should_stop=...)` closes the stream to Ollama and keeps the received text in MIA's history.
- **Tests:** `python tests/test_chat_backend.py` (33 tests: log, mood, service with a fake model, stop, queue, errors, rate limit, REST, two clients).

## Chat page, phase C4 (character integration)

- **Free-area framing:** the page tells the character how much of the window the chat covers
  (`{"type": "viewport_inset", "left", "right", "top", "bottom", "width", "height"}` in pixels, sent at most once per frame, also while the panel is
  dragged or the sheet snaps). `main.gd` eases the camera so the character appears in the middle of the free area (side panel: left of it; bottom
  sheet: above it) and keeps the figure inside the free height. Insets are clamped to 90% of the window; a message without a window size or with
  non-numbers is refused. Collapsing the chat gives the whole window back.
- **View and background:** new bridge message `{"type": "view", "name": "body|bust|face"}`. The menu of the page has a camera row and (when there are pictures in the
  backgrounds folder) a background list; both are remembered per device and sent again when the character has loaded.
- **Caption mode:** with the chat collapsed, MIA's current answer appears as a caption at the bottom of the character area (plain text, the end of a long
  answer) and fades out a few seconds after she has finished (longer for longer text). Her own messages (time check) appear too.
- **Optional character:** without WebGL, or when the character does not report `ready` within 30 seconds, the page removes the iframe, shows a small notice and
  the chat keeps working.
- **Tests:** `godot --headless --path ui/godot --script res://tools/test_bridge.gd` (26 checks: the projected position of the character is

## Phase 8: expressions from a description (LLM)

In the expression editor, type what you want ("surprised but trying to hide it") and press **Generate**. MIA's own Ollama makes the expression; nothing leaves your machine.

- **Flow:** the closest existing preset is shown at once (`/api/expression/match`, no model needed), then the model's expression replaces it and is loaded into the sliders as a new,
  unsaved preset. **Keep** saves it (`source: llm`), **Edit** lets you change sliders and press "Save as new" (`source: llm_edited`), **Reject** discards it and brings the
  previous expression back. Offline or with a failing model you get a clear message and the expression from before stays.
- **Backend (`expression_llm.py`, routes in `presets_api.py`):** `POST /api/expression/generate {"description"}`, `POST /api/expression/match`, `POST /api/expression/feedback
  {"id", "decision": "keep|edit|reject", "preset"?}`. They need the editor token, JSON and a known origin like every write. One request at a time (others get 429), a model
  that cannot be reached gives 503, two unusable answers 502.
- **The prompt:** the 57 shape keys with categories and descriptions, the head/eye bones with their directions, the gestures, rules (3-10 keys, left/right keys for asymmetric looks,
  no vowel keys), and examples: what you kept or edited before (as good examples), what you rejected (marked "do not repeat"), then presets similar to the request.
- **Structured output:** the model must answer with a JSON schema in which every shape key is a number from 0 to 1, so it cannot even name an unknown key. The answer is checked like
  any preset (unknown keys removed, values clamped, corrections shown), a second try is made on an unusable answer.
- **Feedback log:** every request and decision is appended to `data/feedback_log.jsonl` (`feedback_log` in `setup_cfg.json`), not in version control.
- **Model:** by default the model MIA is using right now with the same options (`num_ctx` ...), so Ollama does not have to load a second model or reload this one.
  `"expression_model"` picks another model (then the first request loads it), `"expression_temperature"` (default 0.7) the creativity.
- **Tests:** `python tests/test_expression_llm.py` (21: prompt, validation, retry, offline, busy, match, feedback and examples, REST), `test_editor.gd` (67 checks incl. the UI flow),
  and live over real HTTP: `python ui/tools/expression_stub_server.py` (fake model), then `MIA_URL=http://127.0.0.1:8685 MIA_TOKEN_FILE=data/editor_token.txt
  MIA_EXPRESSION_LIVE=1 godot --headless --path ui/godot --script res://tools/test_editor_live.gd`. Not tested here: the quality of a real model's answers; try a few descriptions
  and use Reject / Keep so the next prompts learn from them. Rebuild the web export (`ui/tools/build_web.sh`) after pulling this phase.

## Phase 9: remote access (optional)

`tailscale` program, also for the script). Not tried against a real Tailscale: `tailscale serve` asks you once to enable HTTPS in the admin console and prints a link for it.

### Editor token in the chat page, and keyboard focus in the editor

Typing into the Godot canvas in a browser can be sluggish (the canvas needs the keyboard focus). So the token no longer has to be typed there: **menu > Settings > Editor token**
is a normal input of the chat page; it stores the token under the key `mia_token`, the same one the editor reads (`preset_api.gd` reads it again for every request, so a token
entered in the page works without reloading the editor tab). The editor's own Token field still works. Text fields of the editor also ask the browser to focus the canvas when
you enter them (`HostBridge.focus_canvas`). `ui/tools/browser_check.py` got `--local-storage key=value` to test such flows.

## The voice in the page: one page plays (fix for echo and a stuck "talking" state)

Every open page (a second tab, the phone next to the computer) is a socket client. Before, all of them played every line and each one deleted the shared
`out.wav` when it ended, so lines were heard twice or three times (an echo, the idle clip too), and a page whose file had just been deleted by another one
never got its "playback ended": the character stayed in the talking pose. Now:

- **One page plays** (`audio_router.py`): a page that is visible claims the voice (`audio_claim`, again when it gets focus or is touched), the others are told
  (`audio_owner`) and stay silent. The new lines (`audio_reload` with `url` and `serial`) go only to that page. Nobody claimed: the page that connected last gets
  them, a closed page hands the voice on. The intro sound plays on the page that was just loaded.
- **Every line has its own file** (`templates/audio/line-<serial>.wav`, the latest 12 are kept, never cached): no shared file, nothing to delete early.
- **The page queues lines** (`sound.js`): a line that arrives while another plays waits and is played after it, nothing is cut off.
- **"Talking" ends**: the mouth follows the queue (on while lines play, one "off" when the queue is empty, no flicker between sentences); the page repeats "speaking"
  every 1.5 s and the character stops talking by itself 5 s after the last signal (`SPEECH_WATCHDOG`, a lost "off" can no longer leave it talking). If an answer fails,
  the character returns to idle.

## Gestures from angles (gesture editor, step 1: server side and character)

A gesture made in the editor is **only its final pose**, given as a few angles; the motion is the interpolation from the neutral pose (the relaxed arms) to that pose in `reach`
seconds, held for `hold` seconds, then the arms ease back. No keyframes to record. What is not set is neutral, so a pose lists only what changes.

- **The sliders (`pose_model.py`, served as `GET /api/pose-model`, converted by `ui/godot/pose_model.gd`):** per arm (the same numbers for both arms, the left one mirrored):
  `upper_raise` 0..180 (hanging ... level ... up), `upper_direction` -120..180 (0 sideways, 90 forward, 180 across, -90 backward), `elbow_bend` 0..150, `elbow_turn` -180..180
  (the forearm swings 0 forward, 90 inward, -90 outward), `hand_turn` -180..180 (0 palm to the body, 90 forward = towards the viewer), `wrist` -70..70, `fingers` (a name, or
  `thumb/index/middle/ring/little` 0 open ... 100 closed). Torso: `torso_lean` (+ forward), `torso_side` and `torso_turn` (+ to the character's left). Neutral values reproduce the
  relaxed arm of the engine. All angles are in the character's frame, not relative to the torso: "forward" is always towards the viewer and a hanging arm stays hanging when the torso
  leans; only the shoulders move with the torso. The torso is shared by `Spine`, `Chest` and `UpperChest` (30/30/40 %) on top of the breathing.
- **Server (`gesture_store.py`, routes in `presets_api.py`):** one JSON file per gesture in `data/gestures` (`gestures_dir`): `{"name", "kind": "pose", "description", "expression", "reach",
  "hold", "pose": {"R": {...}, "L": {...}, "torso": {...}}, "source"}`. `GET /api/gestures` lists the built in (`kind: "keys"`, `builtin: true`, read only: they come with the character and
  their names cannot be reused) and the ones of the editor (`pose_gestures`, complete); `GET/POST/PUT/DELETE /api/gestures[/<name>]` with the same rules as presets (token, JSON, origin;
  values are clamped and unknown ones removed with a message; an empty pose is refused; a gesture that presets use is not renamed or deleted without `?force=1`). Presets and the
  expression generator accept the new gestures. The version number of `/api/presets/version` now covers presets and gestures together, so other devices load both.
- **Character:** `PresetApi` loads the gestures with the presets (`gestures_received`, `create_gesture` / `update_gesture` / `delete_gesture`), `GestureEngine.set_pose_gestures()` converts them
  into the keys the engine plays (they can be played from the menu, by presets and by the page like the built in ones); finger curls in percent are supported by the engine too.
- **Tests:** `python tests/test_gestures_api.py` (26), `godot --headless --path ui/godot --script res://tools/test_pose.gd` (48: the angle conversion, playing, torso, fingers, gestures coming and
  going), `ui/godot/tools/pose_sheet.gd` renders pose documents to pictures (front and side) for a visual check. The slider UI of the editor is the next step.

### The gesture editor (step 2: the sliders)

Open it from the chat page menu ("Gesture editor"), the character's Menu, the "Gestures" button of the expression editor, or with `/character/?gestures`.

## Core, phase 2a: the web tools (search and page fetcher, safety rules)

`web_tools.py` gives the pipelines two tools, `web_search` (budget key `search_calls`) and `fetch_page` (`fetch_calls`); a skill lists them under `tools:`.

- **Search**: backends in order, `search_backends` (default `["searxng", "duckduckgo"]`). A backend that fails or finds nothing hands over to the next; the answer says which
  one was used, what failed and which engines SearXNG could not reach. Duplicates (same page with tracking parameters, `www.`, fragments) are merged, results that point to
  private addresses are dropped. "Nothing found" is an answer, not an error; only "no backend answered" is an error.
- **SearXNG** (self-hosted, the first choice): `tools/searxng/run.sh` starts it with podman or docker on `127.0.0.1:8590` (`stop`, `check` also exist). Its settings enable the
  JSON output. Upstream engines (Brave, DuckDuckGo, ...) sometimes throttle it; `check` and the status block show that. Settings: `searxng_port` (default 8590, used by MIA and by `run.sh`; 8888 is taken by too many other programs) or `searxng_url` for another address.
  It is not started by MIA and does not restart with the machine unless you set that up (the image is about 270 MB).
- **DuckDuckGo** (the fallback): no install; it reads the HTML result page (there is no official free API), waits at least 1.5 s between requests and reports a CAPTCHA or rate limit.
- **Fetching** (`WebClient`): only http(s) to public addresses on ports 80, 443, 8080, 8443; the address is checked before the connection, at every redirect (at most 4) and for the
  address that was really connected. Blocked: localhost, the LAN, the tailnet (100.64.0.0/10, `.ts.net`), link-local and cloud metadata addresses (169.254.169.254), IPv6 private ranges,
  names without a dot or ending in `.local`/`.internal`, addresses with a user name. Limits: 5 s connect, 15 s read, 2 MB, content types html/plain/json/xml, no cookies, no scripts.
- **Text from pages**: scripts, styles, menus and **hidden elements** (`display:none`, `hidden`, `aria-hidden`, font size 0) are dropped, because hidden text is a favourite place for
  instructions aimed at models. `chunk_text` cuts long pages at paragraph breaks.
- **Web text is data** (X1): `untrusted()` wraps it in delimiters that the page cannot close, `injection_signals()` flags phrases like "ignore previous instructions" (shown in the
  status block and logged; a hint, not the protection: the protection is narrow tools and schemas in the stages that read the web).
- **What MIA asked the internet** (X4): every search and fetch is a line in `data/runs/web-YYYY-MM.jsonl` (query, backend, results, errors, URL, status, bytes, timing).
- Other keys (optional): `web_timeout` (`[5, 15]`), `web_max_bytes`, `web_max_chars`, `search_results`.
- Try it without MIA: `python tools/try_search.py "query"`, `--fetch 2` to read the first results, `--url ...`, `--backends duckduckgo`, `--safety` (shows what is blocked).
- Tests: `tests/test_web_tools.py` (no network; fakes for sessions and name resolution).
- A limit worth knowing: the check of the connected address uses the socket of the connection when the library gives it, and the name is resolved by the system a second time when
  the connection is made. A name that changes its address between the two lookups is therefore caught by the connected-address check, not by the first one.

## Core, phase 1b: the library of nodes and pipelines

The design is in `REQUIREMENTS_CORE.md` section 4a. Nodes (reusable steps: checks, model views, tools, code) and pipelines (graphs that wire nodes by reference) are versioned
files; a skill names a pipeline, and the old `pipelines/` folder is gone.

- Files: `library/nodes/<id>/<version>.json` and `library/pipelines/<id>/<version>.json` are shipped (reviewed with git); `data/library/` has the same structure for entries of the user and
  of models, and `status.json` with the decisions about status. A version is immutable: a changed entry is a new version. The index `data/library.sqlite` (entries, dependencies,
  statistics, cases) is rebuilt from the files at start and can be deleted.
- A pipeline node is `{"id": "q", "use": "check.quote@1", "wire": {"quote": "$input.q"}, "params": {...}, "output": "v"}`. The version must be pinned. `wire` must match the declared inputs,
  `params` the declared parameters (defaults apply); wrong wiring is reported when the library loads, a broken pipeline is skipped, not fatal. The safety flags (`reads_web`, `runs_code`) of
  the nodes add up for the pipeline, and the skill must allow them (`max_safety: {reads_web: true}` in its front matter), otherwise the run is refused.
- A skill's `pipeline: summarize` takes the highest version that is `tested` or `trusted`; `summarize@2` pins one (a draft may be pinned for trying it). Statuses: draft, tested, trusted, retired;
  `promote` records your decision in `status.json`, shipped files never change.
- `select` answers which entries fit a task (tags, what they apply to, time and token budget, tools and sandbox available, web/code allowed) with the reasons for each choice and each drop;
  ranking uses specificity, status and the measured results from the run log (from 3 runs on). Planning steps can call it as the tools `library_select` and `library_describe`
  (a skill lists them under `tools:`). Cases (a claim, what was applied, the verdict, the outcome) can be stored and found by common tags.
- Models can only add **drafts** (`Library.add_draft`), never trusted entries; script nodes cannot run yet (the sandbox is not built).
- First entries: the pipelines `chat` and `summarize`; the nodes `code.converse`, `view.summarize`, `tool.web_search`, `tool.fetch_page`, `code.chunk_text`, `code.untrusted_wrap`,
  `check.injection_signals`. The runs record the library entries they used (`uses` in the run log, `library` in the events).
- Config keys (optional): `library_dir`, `user_library_dir`, `library_index`.
- Tool: `python tools/library.py list | search | show | validate | reindex | stats | select | promote | diff | used-by` (see its help).
- Tests: `tests/test_library.py` (34 tests: validation, file rules, wiring, versions, status, index, selection, statistics from real runs, cases, drafts, safety).

## Core, phase 2b: the hard checks as library nodes

`checks.py` holds the checks of `REQUIREMENTS_CORE.md` 12.2, the library holds them as nodes (`library/nodes/check.*`). Every check answers `{status: pass | fail | inconclusive | not_applicable, detail, evidence}`.

| Node | Claim type | What it decides |
|---|---|---|
| `check.quote_in_source` | quotation | the quote occurs in the source (typography, case and spaces normalised, `...` skips text); a near match is `inconclusive` and shows the closest passage |
| `check.arithmetic` | numeric | `expression = value` within a tolerance and the rounding the claim shows (at most 2 percent of the value); no `eval`: two evaluators (float and 40-digit decimal) must agree |
| `check.unit_conversion` | unit | length, mass, time, volume, speed, area, data, energy, pressure, temperature |
| `check.date_claim` | date | weekday of a date, days between, date plus days, age, leap year, before/after |
| `check.schema_valid` | structured | a value fits its JSON schema |
| `check.schedule_overlap` | schedule | no overlapping events, none ends before it starts |
| `check.citation` | citation | the cited page loads (404/410 fail, timeouts and PDFs are inconclusive), is not a search page, contains the quote or has a matching title |
| `check.web_confirm` | fact | needs 2 independent domains (mirrors count once) that contain all facts, query built from entities and numbers, never from the claim's wording, and a disconfirming search ("myth", "false"); never `fail` |

- **Dispatcher**: the nodes `code.hard_checks_offline` and `code.hard_checks_web` take a claim `{type, text, data}`, ask the library for the checks tagged `check` that declare the claim type,
  run the cheap ones first (a `fail` stops the rest) and combine them with one rule (`checks.combine`): any fail = `contradicted`; all applicable pass = `supported`; anything else = `open`
  (a pass is evidence, not proof); nothing applicable = `none`. The web variant reads the web, so a skill using it declares `max_safety: {reads_web: true}`.
- A disputed fact needs a correction marker within about 90 characters of the fact in a search snippet: the disconfirming query attracts pages about myths in general, and those mention
  the fact in passing (found and fixed with the real search).
- Try them: `python tools/try_checks.py` (examples without web access), `--web` (also citation and web confirmation), `--claim '{...}'`, `--list`.
- Tests: `tests/test_checks.py` (39 tests; the web checks run against fake search and fetch; a test keeps the library entries and the code in step).
- Not built yet: the sandboxed script check, the research pipeline that extracts claims, and the harness that measures precision and coverage of the checks.

## Core, phase 2c: the sandbox and the web broker

`sandbox.py` runs code that MIA did not write (model-written verification scripts first). The **wall** is made of operating system features, not of Python:

- **bubblewrap** (`bwrap`): new user, pid, ipc, uts, cgroup and **network** namespaces. The script sees the Python standard library (read-only), an empty `/tmp` of limited size, its own input and nothing else:
  no home directory, no `/etc`, no project files, no environment variables, no network (not even this machine's localhost, which in the sandbox is an empty network of its own). The root is read-only.
- **seccomp filter** (built in `seccomp_program()`, x86_64): no new processes (fork, vfork, clone without `CLONE_THREAD`, clone3 answers "not implemented" so threads still work), no ptrace, mount, unshare,
  setns, bpf, io_uring, kernel modules, keyrings, perf; the 32-bit system call table kills the process.
- **limits**: address space, CPU time, file size and open files inside; a wall-clock timeout from outside kills the whole sandbox; stdout and the result are capped.
- **On top, convenience layers** (not the boundary): an AST policy (`check_script`: allowed imports only, no `open`/`eval`/`exec`, no dunder tricks) and a restricted namespace in the runner. They give clear
  messages and are tested separately; `tests/test_sandbox.py` tests the wall with both switched off (`policy=False, raw=True`) and with the 4 weakest points of the wall removed one at a time to see the tests fail.
- If bubblewrap or user namespaces are missing, `Sandbox.available` is False and `run()` refuses: the feature is off, never weakened. A run takes about 65 ms.
- A script gets `data` (its input) and sets `result` (JSON). `SCRIPT_GUIDE` is the text for prompts that ask a model to write one.

**Web access for scripts** goes through a broker (`broker.py`), because a sandbox has no network and no curl. The script writes a request line on its standard output (`web.get(url, mode="text"|"raw")` or
`web.search(query)`), MIA answers on its standard input. No socket and no mounted file: nothing for SELinux or the namespaces to get in the way of (a container cannot connect to a socket of an unconfined
process under SELinux, which is how this design was found). The answers come from MIA's own web tools, so a script is held to the same rules (public addresses only, redirects and connected address checked, limits,
no POST, no cookies, every request in the web log) plus budgets per script (default 5 pages, 3 searches, 400 kB). The script never sees an address or a socket; the name is resolved and connected by the broker.
Forged or broken protocol lines are answered with an error or ignored; the output of a script is capped also while it talks to the broker.

**Two backends, chosen per operation** (`SandboxRouter`):

| Backend | What it adds | Cost |
|---|---|---|
| `bubblewrap` | namespaces, read-only root, seccomp filter, limits | about 65 ms per run, nothing to install |
| `podman` | a rootless container per run (never a pod: pods share one network namespace): no network, read-only root, no capabilities, no-new-privileges, podman's own seccomp profile made stricter (no fork/clone of processes, same list as above), **SELinux confinement** (`container_t` with its own category label), **cgroup limits** (memory, 64 processes, 1 cpu) | about 0.9 s per run, an image of 170 MB (`tools/sandbox/build_image.sh`, once) |

An operation (`Operation`: kind, origin, tainted, stakes) gets the **standard** tier (bubblewrap; many small checks) or the **strong** tier (podman only) when it is exposed or important:
a script with web access (`web_script`), hostile documents to parse (`parse`), input that comes from unchecked web or file text (`tainted`: prompt injection could have shaped the script), code from outside
(`origin: external`), or high stakes. A pure calculation of a library script or of the model on the user's own data is standard. If the strong backend is missing the operation is **refused**
(status `unavailable`, with the reasons) and never silently weakened; `sandbox_degrade: true` allows bubblewrap instead and marks the result `degraded`. Settings (optional): `sandbox_backend`
(`auto`, `bubblewrap`, `podman`), `sandbox_degrade`, `sandbox_image`. Try it: `python tools/try_sandbox.py` (backends and routing table), `--attack` (hostile scripts on the chosen backend), `--script ...`.

- Tests: `tests/test_sandbox.py` (66 tests: policy, seccomp program and podman profile, runs, the wall of both backends, the broker incl. forged lines, the routing decisions).

## Core, phase 2d: script checks

A claim that can be recomputed is checked by a **script that the model writes for it** and the sandbox runs (`check.script`, claim type `computable`; `check.script_web` for scripts that may use the web
broker, claim type `computable_web`, strong tier only). The contract (`sandbox.SCRIPT_GUIDE` is the text for prompts): the script reads `data` and sets
`result = {"holds": true | false, "values": {what it used}, "explanation": "..."}`. Rules that come from the test-oracle problem (HC3):
- a verdict **needs the values**; a script that says true or false without reporting what it used cannot be reviewed and stays `inconclusive`;
- `data` (the input) is **read-only for the script**: no reassigning, no assigning into it (found with the real model, which had re-typed the input including the claimed number at the top of its script);
- the script, its hash, the output, the backend and the tier are in the evidence; scripts with problems are never run (the policy gives the reason) and a crash, timeout or error is `inconclusive`.

The wall depends on the operation (see the sandbox section): the dispatcher passes the claim's `tainted` and `stakes` fields on, and skips script checks when no backend can run them; they are never run unprotected.
Library entries: `check.script`, `check.script_web`, `view.write_check_script` (the prompt), `view.fix_check_script`, the pipeline `verify.computable` (the model writes the script, the sandbox runs it; if it does not work
the model gets the problem and repairs it, at most twice) and the stored script `script.compound_interest` as an example of the **`script` node kind** (a pinned script of the library; a pipeline node can say `"tainted": true` or
`"stakes": "high"`, and a failing script is an error of the node). The dispatchers `code.hard_checks_*` have a version 2 that declares `runs_code`; version 1 is retired. A skill that uses them says `max_safety: {runs_code: true}`.
The skill `verify_computable` runs the pipeline: `python tools/try_pipeline.py verify_computable --input 'claim=...' --input 'data_description=...' --input 'data={...}' ""`.
`Core(..., sandbox=router, broker_factory=...)` switches the script checks on; without a sandbox they are not offered.
Tests: `tests/test_script_checks.py` (29 tests: the contract, every sandbox outcome, the choice of the wall, the dispatcher with and without sandbox, the pipeline with a fake model including repair, script nodes).

## Core, phase 3: the evaluation harness (test first)

Changes to a check, a prompt, a pipeline or a model are judged by running the same suite before and after, not by a feeling (`REQUIREMENTS_CORE.md` 9).

- **Suites** (`eval/suites/<name>/suite.json` + `cases.jsonl`): one case per line with `id`, `tags`, the input (`claim` for the checks, `input` for a pipeline), `truth` (is the claim actually right?) and/or
  `expect` (the exact behaviour a regression wants, for example that a near match stays `open`), and a `note` saying why. Shipped: `hard_checks` (118 cases, deterministic, no model: quotes, arithmetic, units,
  calendar facts, schedules, structure, routing, with traps and a few documented known limits) and `computable` (39 cases for the pipeline in which a model writes the check script, half right and half wrong claims,
  truths computed in Python by the generator).
- **Numbers** (`metrics.py`): for verifiers the dangerous error comes first, the **false pass** (a wrong claim that passed), then false fail, coverage (how much is decided at all), accuracy among the decided and overall,
  precision of pass and of fail; everything with 95 percent Wilson intervals, because 30 cases cannot say much (an honest "0 of 44 false passes" has an upper bound of 8 percent). Also per tag, stability over repeats
  (the same status every time?), cost (seconds, model calls, characters), and the paired comparison of two runs with the exact sign test.
- **Runs** (`harness.py`, `tools/eval.py`): `python tools/eval.py run <suite> [--variant name] [--repeats n] [--tag t] [--model light|full|name] [--pipeline id@version] [--skill s]`; the variant is saved with the run
  in `data/eval/`; `report <suite|file>`, `compare <fileA> <fileB>` or `compare <suite> <variantA> <variantB>`, `list`, `cases <suite>`. A case that breaks the target is an `error:` result, not the end of the run.
- **The rule** from here on: a check or pipeline change that touches behaviour gets a case first (a failing one), then the fix. `tests/test_harness.py` runs the `hard_checks` suite as a regression (every case
  must match, no false pass, deterministic); the model suites are run by hand (`tools/eval.py run computable`) because they need the model and take minutes.
- What the first run of `hard_checks` found: **four false passes** (an exact integer result was accepted within a percentage tolerance, for example `250 * 4 = 1004` or 2 hours as 121 minutes) and a wrong
  expectation about the sharp s (`casefold`). The checks were fixed (an exact result must be matched within the rounding the claim shows, with exact decimals also for huge numbers), not the expectations.
- Tests: `tests/test_metrics.py` (18, hand-counted numbers), `tests/test_harness.py` (19).
- First model baseline (`eval/baselines/computable-gemma4-12b.md`): `verify.computable@1` decided 79 % of the claims (right overall 77 %, 0 false passes in 20 false claims); the harness showed that the statistics cases
  failed because the hand-written description of the data was misread and a `KeyError` did not name the keys. `verify.computable@2` generates the shape of `data` from the real data and names the keys in a `KeyError`:
  coverage 95 %, right overall 92 %, still 0 false passes, 8.4 s instead of 12.7 s per case. The paired sign test gives p = 0.11, so the gain is likely but not proven with 39 cases.
