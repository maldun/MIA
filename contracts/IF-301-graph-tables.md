# IF-301 – Graph table definitions, record checks, conversion, the rule set and the loader of graphs, v5

Owner (provider): N-3.2 Graph tables   Consumers: N-3.1 Storage layer, N-2.3 Workflow management (converts; checks a graph on save with the rule report, v4), N-2.4.1 Pipeline runner (reads; asks the run check before a run, v4; runs the loaded graph, v5), N-2.3 Workflow management (orders the loaded graph, v5); later G-V4.EDIT and G-V4.CONTEXT (the rule report)   Decided by: N-3   Mock complexity: 1 (a fixed list of types and pure functions, nothing stored)   Suites: `tests/acceptance/contract/test_if_301_graph_tables.py` (v1, unchanged) and `tests/acceptance/contract/test_if_301_v2_graph_tables.py` (v2, v3) and `tests/acceptance/contract/test_if_301_v4_rule_set.py` (v4, TC-IF-301-27 on)

What the storage layer needs to know about the tables of workflows and context graphs, and, since v2, about the graphs kept as separate node and edge records. Python calls; draft v0, v1 since A-60, v2 since A-90 (text approved 2026-11-07, D-262 to D-266), v3 since A-167 (scoped IDs of steps and connections, G-V4.GRAPHSTORE.CORE), v4 since A-170 (the registry of kinds, the rule report and the run check, G-V4.GRAPHAPI.RULES, D-417), v5 since A-187 (the loader: one loaded graph for the order, the rules and the run, G-V4.GRAPHAPI.RUN, D-475). The rules of the document form are those of FR-7 and IF-102; the rules of the stored form are those of FR-63 and FR-64.

## What changes against v1
1. Four new tables, all versioned and not deletable: `graph_nodes`, `graph_edges` (REQ-GTB-005, 006, 013), `graphs` (the graph header and its members, D-264) and `skills` (the skill record of REQ-WFM-040, D-264). `workflows` and `context_graphs` stay as they are (document form, REQ-GTB-015). `definitions()` stays the v1 result; the four tables are listed by the new `record_definitions()` (owner, 2026-11-07: the v1 suite and REQ-GTB-001 say exactly two tables for `definitions()`).
2. A fixed list of node types built into the Graph tables: a node's JSON field names a type ID; each type has a data class and a JSON schema (REQ-GTB-009, 011). A new type is an amendment of this interface (owner, 2026-11-07).
3. New refusals `unknown_type`, `schema_break`, `unknown_member` and `unknown_endpoint` (REQ-GTB-010, 011, 019, 020) and the rule that a refused edit leaves the stored version alone (REQ-GTB-016).
4. Conversion between the record form and the document form of v1 (REQ-GTB-015).

## What changes against v2 (A-167)
1. A record of `graph_nodes`, `graph_edges`, `context_nodes` and `context_edges` carries the ID `<graph id>/<local id>`: the text before the first slash is the graph ID, the rest the local ID, both non-empty (REQ-GTB-029, REQ-GTB-031). Any other ID is `{"rule": "unscoped_id", "detail": <the record ID>}`.
2. A graph header (`graphs`) names only members whose ID begins with `<its own ID>/`; another member is `{"rule": "unscoped_id", "detail": <that member ID>}` (REQ-GTB-030). This is checked with and without `stored`, member by member before `unknown_member`.
3. The ends `from` and `to` of an edge are the scoped IDs of its nodes, so `unknown_endpoint` names a scoped ID. The IDs of `graphs` and `skills` records are not scoped.
4. A caller of v2 that writes plain IDs is refused; the Workflow management (N-2.3) scopes the IDs when it saves a graph and strips them when it reads one (REQ-WFM-144).

## What changes against v3 (A-170)
1. Three new operations, offered by the new module `graph_rule_set` of N-3.2 (D-417): `kinds()` (the registry of kinds), `rule_report(graph)` (every broken rule of a graph in stored form) and `run_check(graph, given=None)` (what stops a run). Every operation of v3 is unchanged; the v1 to v3 suites pass unchanged (REQ-GTB-052).
2. The rules of a graph in **stored form** are written once, per kind of graph, in the registry: `workflow` has eight rules in a fixed order and can run, `context` has three of the same definitions and cannot run (REQ-GTB-033 to 036; D-375, D-404, Q-3).
3. The document form keeps `validate` and its five rules exactly as in v1 (Q-6); G-V4.MIGRATION retires it.
4. Decision 1 of 2026-11-07 ("graph rules stay in the Workflow management only", D-262) is superseded for the stored form by decision 18: the Graph tables offer the rules, the Workflow management and the Pipeline runner ask them.

## What changes against v4 (A-187)
1. One new operation, `load(graph)` (D-473 (2), D-475 (1)): a graph in stored form becomes a networkx `MultiDiGraph` (pinned `networkx==3.7`), the one loaded graph the order (N-2.3), the rules of this interface and the run (N-2.4.1) read. Every operation of v4 keeps its signature and its answers (REQ-GTB-060); the v1 to v4 suites pass unchanged.
2. Inside N-3.2 the rules about adjacency, one writer, session setting and stop limit, cycle and unsupplied inputs read the loaded graph; the rules about step identity, kind of step, connection ends and duplicate connections stay on the stored form, where malformed items are seen (REQ-GTB-059).
3. A mock of `load` is the real `load`: it is a pure function of networkx and the stored form (mock complexity 1).

Record shapes of the two new tables (D-264): a graph header is `{"id", "data": {"kind": "workflow" or "context", "context_graph_id", "testbench_id" (may be empty), "description", "nodes": [{"id", "version"}], "edges": [{"id", "version"}]}}`; a graph version pins the version of each member, so "graph X, version n" is found from its header and an edit of one node makes a new graph version. A skill is `{"id", "data": {"command", "workflow_graph_id", "context_graph_id"}}`; that no command is used twice is a rule of the Workflow management (REQ-WFM-042), not of this interface.

The Workflow management calls `check_record` itself before it writes and so receives the rule and the detail it names in its refusal; the Storage layer calls it again as a guard. IF-102 does not change (D-264).

The Storage layer calls `check_record` before every write and writes nothing when it returns a rule; the version counter is changed only by a write that passed (REQ-GTB-016).

Rules of the stored form in detail (v4, REQ-GTB-041 to 051). "Existing step": a step of the graph whose ID is a non-empty text. The type of a step is `data["type"]`; the role and name of a connection are `data["role"]` and `data["as"]`. A connection is identical to an earlier one when start, end, role and name are all equal.

| Order | Rule | Broken by (parts named) | `text` |
|---|---|---|---|
| 1 | `step_identity` | a step whose ID is not a non-empty text, or repeats the ID of an earlier step (that ID, as text); a slash inside an ID is allowed (REQ-GTB-029, Q-4) | a step has an empty name or a name used twice |
| 2 | `step_kind` | a step whose type is none of `data`, `transform`, `master` (its ID) | a step is not a data, processing or loop-controlling step |
| 3 | `connection_endpoints` | a connection whose `from` or `to` names no existing step (its ID) | a connection leads to or from a step that does not exist |
| 4 | `duplicate_connection` | a connection whose ID repeats that of an earlier connection, or that is identical to an earlier one (its ID) | the same connection is there twice |
| 5 | `adjacency` | a connection between two existing steps that are both of type `data` or both not of type `data` (its ID) | a connection joins two data steps or two steps that are not data |
| 6 | `single_writer` | a data step that connections from more than one existing step lead into (its ID) | a piece of data is written by more than one step |
| 7 | `stop_limit` | a `master` step without a valid stop limit (as `check_record`: `stop` with `max_repetitions` an integer of at least 1 and/or `max_seconds` a number above 0), then a `data` step whose data holds the key `stop` or `session`, then a step that more than one connection with the role `settings` leads into (its ID) | a session setting is wrong: a data step holds a stop or session setting, a step has more than one settings connection, or a loop-controlling step has no valid stop limit |
| 8 | `cycle` | only while rules 1 and 3 are kept: the steps cannot be put in an order; the parts are one cycle with its first step repeated at the end (as `validate`) | the steps run in a circle |
| – | `unknown_kind` | the kind is not in `kinds()` (the kind as text) | the program does not know this kind of graph |
| – | `kind_cannot_run` | `run_check` only: the kind has `"runs": false` (the kind) | a graph of this kind cannot run |
| – | `unsupplied_input` | `run_check` only: a connection from a `data` step into a `transform` or `master` step, without the role `settings` or `order`, whose data step has no connection leading into it, no `value` other than `null` in the graph and is not in `given` (the data step) | an input of the step has no writer, no start value in the graph and no value given with the run |

Malformed input (REQ-GTB-040): a step that is not an object, or has no text ID, is rule 1 (its ID as text, `"None"` when missing); a connection that is not an object, or has no text `from` or `to`, is rule 3 (its ID as text); data that is not an object counts as empty data (the record checks refuse it on save as `schema_break`); `nodes` or `edges` that is not a list is rule 1 or rule 3 with the part `nodes` or `edges`; a graph that is not an object gives `[{"rule": "step_identity", "parts": ["graph"], ...}]`. The prototype raised on such input (finding 4); the parts named were chosen by the owner (D-418 (2)).

The Workflow management asks `rule_report` on every save, after the check of the kind and before the record checks, and refuses the save naming every item, so a graph that breaks rules is refused with all of them even when a record would also be refused (REQ-WFM-162, 163, 150; corrected by A-185, Verify V-2); the Pipeline runner asks `run_check` before the first step and runs nothing when it says `refused`; trust is checked after it (REQ-RUN-036 to 038, D-416 (3)).

Rules in detail of the document form (A-60, D-160, D-162) are as in v1:
- `node_identity`: every node has a non-empty text `id`, unique, and a `kind` of `process` or `data`; every edge is `{"from", "to"}` with two text ids of known nodes. A document whose `nodes` or `edges` is not a list, a node or edge that is not an object, and an edge endpoint that is not text (a list, an object, a number) are `node_identity`.
- `session_stopping_criterion`: a process node with `session: true` has a `stop` object with `max_cycles` or `max_seconds`; each limit that is given is a positive integer (an integer >= 1, not a boolean; `-1`, `0`, `"3"`, `true`, `2.5`, NaN are refused), and a limit that is `null` counts as not given (D-162). A `stop` that is not an object is this rule too.

## The fixed list of types (field names confirmed by the owner in D-264)
Workflow nodes only (D-263); the rules of the whole graph are checked by the Workflow management (D-262). Besides `type`, the JSON field of a node holds:
| Type ID | Field | JSON kind | Required | From |
|---|---|---|---|---|
| `data` | `value` | any JSON | optional | REQ-WFM-049 |
| `data` | `parameters` | object | optional (empty object if absent) | REQ-WFM-049 |
| `transform` | `toolbox_id` | string | required | REQ-GTB-007 |
| `master` | `toolbox_id` | string | required (a master node runs like a transform, REQ-RUN-018) | REQ-RUN-018 |
| `master` | `stop` | object with `max_repetitions` (integer, at least 1) and/or `max_seconds` (number, above 0), at least one of them | required | REQ-WFM-048, REQ-GTB-008 |
| `master` | `task` | object, shape open until the debates goal | optional | REQ-GTB-008 |
The graph description (ID, context graph ID, testbench ID, description) is not a node field: it is in the graph header.

The list is closed for the fields of a type too (A-93, REQ-GTB-022): the schema of each type sets `additionalProperties: false`, so the JSON field of a node holds `type`, the fields of the table above and nothing else. A node with another field, or with a key `id` inside `data`, is `{"rule": "schema_break", "detail": "<that field>"}` in `check_record` and in `to_object` (a stored node is refused on read; `to_object` never raises). This holds for workflow nodes only: the schema of a context-graph node comes from its categories (decision 5). The schemas that `types()` returns carry the setting.

## Context graph tables (A-98, F-02)
- `record_definitions()` lists six tables: the four above and `context_nodes` and `context_edges` (versioned, not deletable). `definitions()` stays the two tables of v1. The nodes and the edges of a context graph are kept in these tables, the graph header in `graphs` with `kind` `context` (REQ-GTB-023).
- `check_record("context_nodes", record, categories=None, stored=None, record_id=None)`: a record `{"id", "data"}` with a non-empty text `id`, a JSON field that is an object and a non-empty text `type` in it; otherwise `record_identity` (detail `id`) or `schema_break` (detail `data`, `type`). Without `categories` nothing more is checked: the Storage layer calls it this way and checks the shape only. With `categories` (the caller passes them, as in golden 13) the type must be one of them (`unknown_type`) and the field must fit its schema (`schema_break`) (REQ-GTB-024).
- `check_record("context_edges", record, ...)`: a record `{"id", "from", "to", "data"}` as `graph_edges`, with `data` an object; with `stored` the two ends must be stored context nodes, `stored["context_nodes"]` being `{id: [versions]}`, else `unknown_endpoint` naming the end. A workflow node does not count (REQ-GTB-025).
- `check_record("graphs", header, stored=...)`: for `kind` `context` the members are looked up in `stored["context_nodes"]` and `stored["context_edges"]`, for `kind` `workflow` in `stored["nodes"]` and `stored["edges"]` as before; a missing member is `unknown_member` (REQ-GTB-026). A missing key of `stored` counts as no records.
- Input that cannot be checked (REQ-GTB-027, F-09): a record nested deeper than 200 levels (the record itself is level 1) is `{"rule": "schema_break", "detail": "data"}`; a category whose schema is not a valid JSON schema is `{"rule": "schema_break", "detail": "type"}`, for a record of `graph_nodes` and of `context_nodes` alike. Nothing raises, in `check_record` and in `to_object`.
- What a level is (F-23, A-104): levels are counted down the path from the record. The record is level 1 and every value below it, an object, a list or a scalar, is one level deeper than its parent, so a scalar inside the 200th object is level 201 and refused, an empty object at level 200 is accepted. The Storage layer counts a document the same way (REQ-SLY-013). A tuple is counted like a list (F-24).
- Size (REQ-GTB-028, F-22): a record with more than 100,000 values is `{"rule": "schema_break", "detail": "data"}`. A value is counted once for every path that reaches it (a value reached twice counts twice); the record itself, every object, every list and every scalar count. The count stops at 100,001, so a record that shares sub-objects (2**30 paths) is refused at once. Nothing raises, in `check_record` and in `to_object`.
- `check_record("graph_nodes", ..., categories=...)` and golden 13 stay as they are.

## Golden examples
1. Typical: a valid lookup graph gives `None`.
2. Failure: an edge between two data nodes gives `adjacent_data_nodes`.
3. Edge: `p->d->p` gives `cycle` with detail `["p","d","p"]`; a session node with `max_cycles: 0` and no `max_seconds` gives `session_stopping_criterion`.
4. Malformed (A-60): a session node with `stop: "x"` or `max_cycles: -1`, `"3"`, `true` or `2.5` gives `session_stopping_criterion`, with `max_cycles: 1` it is valid; an edge `{"from": ["q"], "to": "p"}` gives `node_identity`.
5. Typical (v2): a `transform` node record with a known type and a field that fits its schema gives `None`; `to_object` returns an instance of the listed class with equal values.
6. Failure (v2): a node whose `data.type` is `x.unknown` gives `{"rule": "unknown_type", "detail": "x.unknown"}`.
7. Failure (v2): a node whose required key is missing gives `{"rule": "schema_break", "detail": "<path of the key>"}` (the path as the pinned validator names it, TR-GTB-003).
8. Edge (v2): a refused edit leaves version 1 as the latest version (REQ-GTB-016); `check_record` itself stores nothing and changes neither its input nor `stored`.
9. Compatibility (v2): `from_document(to_document(g))` equals `g` for a graph without a master node; the v1 suite passes unchanged.
10. Header (v2, IDs scoped in v3): a `graphs` record `wf1` naming `wf1/n1` at version 5 with `stored = {"nodes": {"wf1/n1": [1, 2]}, "edges": {}}` gives `{"rule": "unknown_member", "detail": "wf1/n1"}`; naming version 2 gives `None`.
11. Edge (v2, IDs scoped in v3): an edge `g/e1` from `g/n1` to `g/n9` with `stored["nodes"] == {"g/n1": [1]}` gives `{"rule": "unknown_endpoint", "detail": "g/n9"}`.
12. Skill (v2): `{"id": "lookup", "data": {"command": "/lookup", "workflow_graph_id": "wf-lookup"}}` (no context graph ID) gives `{"rule": "schema_break", "detail": "context_graph_id"}`.
13. Context graph (v2): a node of category `entity` with `categories = {"entity": <schema>}` and a field that fits gives `None`; the same node without `categories` gives `{"rule": "unknown_type", "detail": "entity"}`.
14. Document form (v2): `to_document` of a graph with a master node gives `{"refused": {"rule": "not_representable", "detail": "<master node ID>"}}`.
15. Record identity (v2, IDs scoped in v3): a node record whose `id` is `g/n1`, checked with `record_id="x"`, gives `{"rule": "record_identity", "detail": "id"}`; with `record_id="g/n1"` or without `record_id` it gives `None`.
16. Extra field (v2, IDs scoped in v3): a node record `{"id": "g/d1", "data": {"type": "data", "foo": 1}}` gives `{"rule": "schema_break", "detail": "foo"}` in `check_record`, and `to_object` of it gives `{"refused": {"rule": "schema_break", "detail": "foo"}}`; a key `id` inside `data` is named `id`; the same node without the extra field gives `None`.
17. Context node (v2, IDs scoped in v3): `{"id": "cg/c1", "data": {"type": "entity"}}` checked as `context_nodes` without `categories` gives `None`; `{"id": "cg/c1", "data": {}}` gives `{"rule": "schema_break", "detail": "type"}`; with `categories = {"entity": <schema>}` and a field that breaks the schema it names that field.
18. ## Decisions of the owner, 2026-11-07 (D-262, D-263, D-264, D-266)
1. **Graph rules for the new node types** stay in the Workflow management only. IF-301 keeps the v1 rules for the document form and adds only the record rules; A-90's "validate also reports ..." is read as `check_record`.
2. **Refusal** is a result with the rule, as in v1 (A-60), not an exception.
3. **Master node in the document form:** `to_document` refuses with `not_representable`.
4. **Types** of workflow graphs are a fixed list inside the Graph tables, not registered by other parts. Adding a type is an amendment of this interface.
5. **Context graphs (D-263):** no fixed list. A context-graph node names a category whose JSON schema comes from the context graph's own definition (FR-41, goal C); the caller passes it as `categories`. Where that definition is stored is decided in goal C; in G-V2 no context graph is converted, so only the rule and its checks exist.
6. **Master node (D-264):** `toolbox_id` required, `stop` required, `task` optional.
7. **Membership (D-264):** a versioned table `graphs` holds the header and lists its members with their versions.
8. **Skill record (D-264):** a versioned table `skills` in IF-301; STORE defines it, the Workflow management checks the content.
9. **Refusals (D-264):** the Workflow management calls `check_record` itself; IF-102 is unchanged.
10. **Review of 2026-11-07 (D-266):** `check_record` gets the argument `stored` for the rules that need to know what is stored; `to_document` maps `transform` to `process`; an edge must name stored nodes (`unknown_endpoint`, REQ-GTB-020); golden examples (here 10 to 14) added; stale wording corrected.
11. **Plan step 4 (owner, 2026-11-07):** `definitions()` stays the two tables of v1 and the four record tables come from `record_definitions()`, because the v1 suite (TC-IF-301-01) and REQ-GTB-001 say exactly two tables.
12. **A-92 (found in Implement T-04, 2026-11-07):** a record written under a record ID that differs from the `id` inside it is refused; the rule stays in the Graph tables (REQ-GTB-021), so `check_record` takes the optional `record_id` and the Storage layer passes the ID it writes under. v2 is not merged yet, so the argument is part of v2.
13. **A-93 (Verify finding F-01, 2026-11-07; the owner delegated the choice to the reviewer and may overrule):** the fixed list is closed for the fields of a type too: a node with a field its type does not list is refused as `schema_break` naming the field, on write and on read. Before, such a node was stored and then `to_object` raised (the mock silently dropped the field). Why: the list of types is fixed (decision 4), REQ-GTB-014 needs the round trip exact, and a silent drop would lose data. Context-graph nodes are not affected (decision 5). Several breaks in one record: the detail is the first path in text order, a missing key counting at the path of its object and an extra field at its own path, so a missing `toolbox_id` is named before an extra `foo`. v2 is not merged yet, so this is part of v2.
14. **A-98 (Verify finding F-02, owner's decisions of 2026-11-08):** the nodes and edges of a context graph are kept in their own tables `context_nodes` and `context_edges`, because the Storage layer cannot know the categories of a context graph (IF-102 `put` has no such argument). Symmetric tables, so ends and members of a context graph are looked up inside the context tables. The Storage layer checks the shape only (it calls `check_record` without `categories`); the context-graph owner or the Workflow management calls it with the categories before it writes. IF-102 does not change. v2 is not merged yet, so this is part of v2.

## Clarifications fixed by the v2 mock and suite (for approval with this text; the approved text of D-262 to D-266 was silent on them)
- `types()` returns a dict `{type ID: JSON schema}` whose keys are the three type IDs in sorted order: `data`, `master`, `transform`.
- A node object has the attribute `id` and, for each field of its type in the table above, an attribute of that name (absent optional fields: `value` and `task` are `None`, `parameters` is `{}`); `to_record` leaves `value` and `task` out when they are `None` and always writes `parameters`. A context-graph node object has `id`, `type` and its other fields.
- An edge has no type; the JSON field `data` of an edge must be an object, else `schema_break` with the detail `data`. A record whose `data` is missing or is not an object is `schema_break` with the detail `data`.
- The category of a context-graph node is in `data["type"]`, as the type of a workflow node. Given `categories` (even empty) a record is a context-graph record: its type must be one of the categories.
- The detail of `schema_break` is the path of the field with dots (`stop.max_repetitions`); a missing required key is named by that key. The contract suite fixes only top-level paths.
- An additional field of a node's JSON field is named by its own key (`foo`; `id` for a key `id` inside `data`); when several are extra, the first in sorted order is named (decision 13).
- A graph header that names the same member ID twice is `record_identity` with the detail `nodes` or `edges` (the mock does so; the suite only requires a refusal in TC-GTB-017).
- The document form carries the other fields of a node flat beside `id` and `kind`, and the JSON field of an edge under `data` with its `id`; an edge of a v1 document without an ID gets `e1`, `e2`, ... in order. A node record converted from a v1 document is not checked (a `process` node has no `toolbox_id`, so the record breaks the schema of `transform` until a toolbox ID is added).
