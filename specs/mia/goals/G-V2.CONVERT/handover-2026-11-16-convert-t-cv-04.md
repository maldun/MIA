## The design in one paragraph (decisions D-241 to D-253, all by the owner, reviewer name maldun)
A converted skill is a skill record plus a workflow graph of data, transform and master nodes: stages are transform nodes (the toolbox ID is the node ID of the library node), loops, maps over unknown lists and debates are master nodes with a stop criterion (`control.<kind>` with the construct JSON as settings), a branch of fixed alternatives is a transform. A transform gets `(inputs, outputs, node)` through a `Stage` (names by the edge field `as`, settings by an edge with `role: settings`, the order of independent steps kept by `role: order` edges through extra data nodes, start values: run inputs, then `prepare`, then the graph node's `value`). Tools and the model are JSON descriptors in data nodes, resolved only against what MIA registered (`common_operations.register_tool/register_model`). Code lives in `common_operations.py` (one `FUNCTIONS` dict, same objects as the old registries) and thin toolbox entries that call it, one-off functions stay in the toolbox. IF-301 is unchanged. Details and the owner's answers: the three notes named above and `specs/mia/review-log.md` rows D-241 to D-253.

## Next: T-CV-04 (`run_converted`), and the open question that blocks its first skill
`run_converted(name, inputs, model, tools, skills_dir, library_dir, runs_dir, skill_changes)` (stub in `skill_converter.py`) must, per A-125: load the skill (`skill_store.load_skill`), take its pipeline from `library_dir`, convert it in memory (`pipeline_graph.convert(pipeline, library_nodes, budget_seconds)`), bind it (`bind_skill(graph, library_nodes, skill, skill_changes)`), register the handed model and tools (`register_model(profile, chat)`, `register_tool(...)`), seed a toolbox from `library_dir/nodes` on an in-memory library (`TransformLibraryMock` is test code: use the real `WorkflowLibrary(Storage(FileBackend(tmpdir)))` as `tests/test_toolbox.py` does), build the stages (`stages_from_toolbox`), run `GraphRunner(trust).run(graph, nodes, {"input.<field>": value})` and return an object with `status`, `answer` (the value of the conversion's `result` node) and the data values. `runs_dir` stays unused. Expected after T-CV-04: the TC-WFM-058 subtests of plan_question, verify_claim and extract_claims green (no amendment of the test; verify_computable and research stay red until their tasks, owner's decision Q5 of A-125).
**Open point, needs the owner (put it as a short questionnaire first):** a `run` entry of the toolbox receives only the inputs, so the settings node of a transform does not reach it; `code.pick_field` needs its `path` from the settings node, and extract_claims uses a field reference (`$raw.claims`), so its subtest cannot pass until this is solved. Proposal: `stages_from_toolbox` passes the settings object as an extra argument (for example `settings`) to `run` entries, and `pick_field` reads its `path` from there; it changes the `run(args)` convention of thin entries.
Other things T-CV-04 will meet: `model_step` has no budget, token estimate or run events; the old and converted calls are compared by messages, schema, model, profile and options only. Params of a pipeline node (`params` key) are not converted (none in the five pipelines).
