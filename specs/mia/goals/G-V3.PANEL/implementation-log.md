## Unspecified behavior (decisions no requirement covers)
- T-09: `#character-box` is an invisible marker box for the free area (left of the chat and above the strip, or above the chat on the phone); the character iframe still fills the window and is told the free area by the inset, which now includes the strip height. `#chat` is a wrapper around the content of the panel. The buttons pause, resume and stop are always on the strip and disabled when the state does not allow them (the phone check needs every control to have a 44 px box). DECIDED by the owner (2026-11-11): the 820 px switch is not needed, the chat keeps its old mode switch; the look of the character in the changed box is checked in the Validate phase (VAL-012). Context: REQ-CLV-040/042 say 820 px, but the chat keeps its old mode switch (width >= 600 and wider than high, TC of REQ-CL layout, `core.test.mjs` expects `panel` at 740 x 360): a landscape window of 600 to 820 px still gets the panel at the right with the strip below it, not the stack; 360 x 800 and 1440 x 900 are as required. Not checked: how the character looks in the changed box (the browser checks run with `character=0`); a person has to look at it at the field test.
- T-08: the shares (REQ-CLV-045, -046) were built here, not in T-09, because TC-CLV-036 sets the Full run share: `skill-run-shares.js` keeps both in the browser storage (keys `mia.srv.strip`, `mia.srv.full`), refuses values outside 12 to 40 and 20 to 60 when the input changes, and sets the CSS variables `--srv-strip-share` and `--srv-full-share`; the two inputs are in the settings dialog. The open Full run part floats above the strip (fixed, its own height share), so the strip keeps its share (TC-CLV-045 measures the strip with the part open); the height of `details#srv-full` that the browser checks measure is then only its summary, the real limit is on `.srv-full-body`. The files of a run are listed by name from the record; size, time and task are added when `/api/files` lists the file (the Files tab of the workspace is unchanged). A link to a run that does not exist shows the failure toast. T-09 still has to check the layout (character left, chat right, strip across the full width), the phone stacking and the 44 px targets.
- T-07: the strip is a fixed bar at the bottom for now (the panel's bottom moves up by its height through `--strip-h`); the real layout, sizes and shares are T-09. The Full run part (markup and filling) was built here because TC-CLV-043 reads it; its collapsed start, link, height limit and reload behaviour are T-08. The start time is shown in the browser's local time as hours and minutes; a failed run without a reason shows no reason line, a stopped one without a reason shows `stopped by the user`. The old status card is still drawn beside the strip until T-10. A refetch of the shown run (after `skill_run_changed` and on connect) replaces the view with the record.
- T-05: a failed run's result text is `The /<task> run failed: <reason>` plus the link (until G-V3.CHAT words it); without a recorder (no `votes` storage) the old texts and the `Files:` suffix stay. The record state is never `paused` (only `task_status` says paused). On `failed`/`stopped` the running phase (else the first open one) takes that state. `ChatService` builds its recorder itself from the `votes` storage when none is given. Run ids tie-break by id when two runs share a second.
- T-04: the recorder is only created when `ChatService(recorder=...)` is given; the account of a run without accounts is `page`. The observer swallows and logs an error of the recorder (a failing record must not take the answer away). The result of the record is the text before the `Files:` suffix. Reason of a failed run is the exception text, of a stopped run `stopped by the user`. The recorder makes its own `TaskMonitor`: in T-05 the web application must give the recorder an `emit` that passes only `skill_run_changed`, or `task_status` is sent twice.
- T-06: a status without `state` (today's `task_status`) gets the state done, paused or running from its `done` and `paused` flags; `applyStatus` keeps an ended run only against a later status of the same id that is not ended (a new run with another id replaces it); counts are shown as `String(value)`.
- T-02: on `end` with state `done` all phases of the record become `done`; with `failed` or `stopped` the phase states stay as they were. A phase name that is not declared at `start` changes the monitor's phase text only, not the phase list. A history delete is answered with one `skill_run_changed {id: null}` even if the account had no run record.
