# High-Level Specification: MIA

**Status:** Approved (owner, 2026-10-24: review steps 1 to 7 confirmed, all acceptance criteria accepted; see review-log.md)
**Owner:** Stefan Reiterer   **Date:** 2026-10-24
**Project / deliverable:** MIA, "MIA Is not an Assistant": a personal virtual assistant with a 3D character, a local voice, and a research core for small local language models

Supersedes `docs/fresh-start/02_high_level_requirements.md` (HLR-01..27; mapping in 3.5). Input: `baseline-requirements.md` (what the five requirement documents ask for, with status), `research.md` (facts). Model: `architecture.sysml` and `model/`.

## 1. Context and goal
*Step 1 of the review (2026-10-24), decisions D-1 to D-7 of `review-log.md`: several users with local accounts and passwords, one shared MIA (one memory, one persona), all users see everything. Sections 3 to 6 still describe the single-user draft; the changes they need are listed in the review log and applied in the later steps.*

MIA is built by one person and is to become a **multi-user system**: several users log in, and a database stores information that is shared between apps. Today it runs on one machine for one owner. It is a companion and assistant: a chat page with a 3D anime character that shows emotions and gestures, speaks with a locally synthesised voice and answers with a local language model (`gemma4`). It is also a research vehicle: the project asks how much quality a small, free, local model reaches when it is embedded in pipelines that verify what they say, log what they do and can be measured. The next large goal is a literature review of a research question (reading papers, judging how well the literature answers a question), after the quick fact-check ("lookup") that exists today.
Development is **iterative**: MIA is meant to grow several skills and workflows over time, each added through the same path (skill file, pipeline, suite, baseline, review). **Success** means two things: the first real skill, the **lookup** (it exists today and is simpler), is brought through the path as the documented example for all later workflows and is measured; and a **second skill, the literature review, is added within one month** by the same path, which shows that the path itself works (order decided 2026-10-24, D-37).
The character is the face of the product: it shows a mood in every situation, speaks with an anime-like voice produced by an open TTS (Kokoro) on the host and played in the browser, can be exchanged by loading a VRoid `.vrm` model, follows a persona from `calibration.txt`, and a plus/minus feedback system over several categories shapes its mood and its behaviour over time (details CR-1..CR-8 in `review-log.md`, to become requirements in step 3).
Why a fresh start now: five requirement documents grew side by side with the code, partly contradict each other and are partly out of date; the new development workflow (explore, plan, implement, verify, commit, deploy, validate) needs one specification that everything else traces back to.

### Users and stakeholders
| Who | Role | Main concern |
|---|---|---|

## 2. Scope
### In scope
**Accounts and login for several trusted users, a shared database** for the state that applications share (D-1), and **a graph app** that visualises and edits the workflow graphs on that database (D-9). Everything MIA does on the host: the conversation (chat page, server, history), the embodied character (expressions, gestures, editor), the voice, the task runtime (skills, pipelines, library, strategies), verification and its sandbox, research (lookup now, literature review next), memory and behaviour feedback, the log and its views, the evaluation harness, the operation (configuration, containers, access, shutdown).
### Out of scope (non-goals)
Fine-tuning the Gemma model (until the learning ladder reaches distillation and the owner decides so); a generic workflow engine; legs and feet of the character; voice input, attachments, message editing, push notifications, an installable app and an offline mode of the chat, answers in languages other than English (English only for now, D-36; German texts are a future feature) and translating MIA's answers; paid APIs.
### Future features (noted, not in the first version; D-27, D-28)
- **Skills:** storytelling (a scene loop with a story state; just another skill, to be added through the path of FR-20), schedule, translating.
- **Chat:** export of the conversation, search within the conversation, accent colour presets, German texts. (Regenerate and speak again are in the first version, FR-1; the search command that lists findings from SearXNG is FR-10.)
- **Character:** accessories as props on bones (the model has none today; variants of FR-32 hide, show and recolour parts).
### Known shortcuts (prototype)
The persona is a shared parameter file outside git (`calibration.txt`); the editor and chat have one shared token and no login today (to be replaced by accounts, D-1); Tailscale access has not been tried against a real tailnet; the verification styles and the research suites are starter-sized; evaluation labels were set by the owner alone; SysML text is not parsed by a tool yet.

## 3. High-level requirements
`Status` below: built / partly / proposed / postponed, as in `baseline-requirements.md` (taken from `ui/README.md` and the commit log, tests not re-run today). Baseline ids in brackets.

### 3.1 Functional requirements
- **FR-1 Conversation** [CT-1..CT-9, CT-11] (built; attribution to users proposed). MIA shall let several logged-in users hold a conversation with her in a web browser on desktop and phone, with answers appearing while they are written, a stop button, a queue of waiting messages, a history that survives reload and is shown live on every connected device, every message attributed to the user who sent it, and one shared MIA answering all of them (D-4). The visible history is kept apart from MIA's memory, is bounded in size and can be deleted by a user after a confirmation; the page shows the connection state, reconnects by itself and keeps unsent drafts. Users can have the last answer regenerated and any answer spoken again (D-28).
- **FR-2 Embodied character** [CH-1..CH-10, CH-12, EM-1] (built). MIA shall show her emotional state and speech through a 3D character with smoothly blending facial expressions, arm gestures, a moving mouth while speaking, blinking and idle motion, driven through one central expression API; if the character cannot load, the chat shall still work. The character is the stage: it fills the window and the chat overlays it (a side panel on wide screens, a bottom sheet on phones) and can be collapsed so that only the character and a caption of the last answer remain.
- **FR-3 Voice** [VO-1..VO-4, CT-7] (built; CR-2). MIA shall make the voice of every answer automatically with an open text-to-speech engine (Kokoro for now, replaceable behind one interface), apply a post-processing step that makes it sound anime-like, and play it in the user's browser, sentence by sentence, speaking only what is meant to be heard; every user can mute or stop it for themselves. Short fixed lines for moods and events are FR-31.
- **FR-4 Transparency** [CT-2, LG-1, LG-3] (built). MIA shall tell every user in one short line how she feels and what she is doing, and shall let a user open, for any answer produced by a task, a step-by-step account of how it came about, whose accurate part comes from real event data and never from a model.
- **FR-5 User-shaped appearance and persona** [CH-4..CH-9, CT-2, OP-5] (built; accounts proposed; CR-4). MIA shall let every user change expressions, gestures, backgrounds, mood phrases, emotions and the persona as data without changing code, with an expression editor and a motion editor (today the gesture editor); a saved change applies to all users at once, appears on every connected device without a reload, and is recorded with its author (D-10).
- **FR-6 Tasks as skills** [TK-1, TK-2, RS-1, CT-11] (built for chat, lookup, summarize; storytelling and schedule proposed). MIA shall perform each kind of work as a task defined by a human-readable skill file and a pipeline, selectable by every user; a task that reaches the internet is never chosen silently.
- **FR-7 Workflows as data** [TK-3..TK-5, TK-10] (built as files; database and graph model proposed; extended by amendments 1 to 3, D-41, D-42, D-43). MIA shall define every pipeline and agent workflow as validated, versioned data in a library with a lifecycle (draft, tested, trusted, retired); every edit by a user is a new immutable version with author and time and applies to all (D-10); an entry proposed by a model stays a draft until a user approves it, shown as a diff and tried on the test set. The workflow model is a **directed acyclic graph of two kinds of nodes**, in the manner of P-graphs: **process nodes** (tasks) and **data nodes** (an artifact such as a claim, a page or a result). An edge leads from a data node to the process that reads it, or from a process to the data node that it writes; two data nodes are never adjacent; a data node that no process writes is an input of the workflow; a data node can be read by several processes, so the same input appears once in the model. MIA shall check by an algorithm, when a workflow is saved and before it runs, that it has no cycle, and shall name a cycle that it finds. A debate, a vote or another multi-agent task is **a process inside one node** of kind session: the node holds the configuration of the master that supervises the task, with its stopping criteria (a maximum number of cycles, a maximum time, or both; the first one reached ends it), and the definition of the multi-agent task itself. A session node without a stopping criterion is refused. The cycles inside a node are recorded as events (the field round) and are not part of the workflow graph (amendments 2 and 3, D-42, D-43).
- **FR-8 Model management** [C-1..C-3, CT-11] (built). MIA shall run on a local model server, let any user switch between a light and a full model (the switch applies to all and asks for confirmation, CON-6), free GPU memory on request, and say plainly when the model server is unreachable.
- **FR-9 Verify before asserting** [VE-1, VE-2, VE-4, VE-5, VE-7] (built, not yet measured on holdout). MIA shall check by code what code can check, use model judgement only for the rest, treat "unknown" as a proper answer, and let a failed hard check outweigh any model verdict. Judgement styles (single voice, repeated samples, a jury, for and against with a judge, a trial) are interchangeable, run only on the claims that the hard checks leave open, and have fixed numbers of turns and tokens. Repeating a run on the same input and the same sources gives the same verdicts and the same set of facts and statements; only their order and wording may differ (D-31).
- **FR-10 Lookup** [RS-1, RS-6] (built). MIA shall answer a factual question with the sources and verbatim quotes that support it, prefer a trusted source to a model judgement, and say "unknown" when nothing supports an answer. A search command calls the SearXNG metasearch and lists the findings (title, address, short text) without composing or verifying an answer (D-28). Repeating a lookup on the same sources gives the same facts and statements, with the same number of facts; only order and wording may differ (D-31).
- **FR-11 Literature review** [RS-2..RS-5, RS-7..RS-10, RS-12, RS-14] (proposed; phases 1 to 2b built). Given a research question, an optional field scope, a cut-off date and a budget, MIA shall produce a structured report: sources kept and dropped with reasons, findings per sub-question with verbatim anchors, conflicts, an answerability figure with its parts, open gaps and next keywords; she works in time slices (first 60 s), gives an intermediate report with a recommendation at the end of each, and continues only when the requesting user agrees. She works top down in levels with narrow roles (analyse the question, determine the components, schedule the tasks) and sizes each piece of work to a share of the context window by code; she stops when a check in code finds every sub-question answered or a budget used up, never because the model feels done; names that other fields use for the same thing are proposed as aliases and accepted only with evidence, and each finding records the field whose vocabulary found it.
- **FR-12 Knowledge of sources** [RS-5, RS-6] (built). MIA shall record where a source comes from and how far she trusts it (class, venue, date, peer-review status, retraction status from the metadata), keep the users' edits of that trust and honour a time cut-off strictly.
- **FR-13 Method transfer** [RS-13] (proposed, off by default). On request MIA shall look for methods from other fields that fit the structure of a problem, offering few ranked candidates marked as hypotheses unless an executable test on a toy instance passed.
- **FR-14 Memory** [ME-1, ME-2] (partly: early summary-based dreaming). MIA shall remember the relationship over time: keep the raw conversation, keep structured facts, preferences and commitments linked to their source, consolidate at rest, retrieve what is relevant within the token budget, let every user inspect, correct and delete any record, and never store a fact about a user that came from web or file text.
- **FR-15 Behaviour rules and feedback** [BF-1, BF-2, EM-1, EM-2] (partly: speech rules). MIA shall detect violations of defined behaviour rules, repair them silently, record them as signals and let signals change later behaviour; reward for factual answers comes from checks and sources, not from the users' approval alone (the adaptation to votes is FR-29); no correction enters the conversation memory as a scolding.
- **FR-16 Traceability** [LG-1..LG-4] (built; context assembly in running pipelines proposed). MIA shall write every run as typed, schema-checked events with one run id through every model call, request and check, secrets removed; any statement in an answer shall be traceable to the query that found its source; a recorded run shall be replayable and reproducible offline; two runs shall be comparable. Every run is attributed to the user who started it.
- **FR-17 Measurable quality** [EV-1, RS-14, RS-15] (built). MIA shall be evaluated by a harness that runs pipeline variants on fixed suites with repeats, intervals and cost counting; every behaviour change starts with a test case; improvement claims hold on held-out cases. A model used as a judge is calibrated against the users' ratings before its verdicts count.
- **FR-18 Optional learning** [LN-1, RS-15] (proposed). MIA shall learn only from logged signals (including the votes of FR-27), only in discrete choices of configuration and graph weights, with every learned choice logged next to the default, switchable off and reversible.
- **FR-19 Operable** [OP-1..OP-3, OP-6] (built). MIA shall be installable and runnable from one configuration file and one command (virtual environment or compose stack), shut down in an orderly way that saves her memory, back up and restore her data, and report missing options after an update. At installation the owner creates the first account; the database is part of backup and restore.
- **FR-20 Skill development path** [TK-2, TK-4, TK-6, EV-1] (proposed; D-2, D-8, D-10). MIA shall provide one documented path from an idea to a promoted skill, open to every user: a skill file and a pipeline built from library nodes and validated before use; the specification and benchmark of FR-26 before the skill is trusted; a declaration of the skill's model, tools, budgets and trust boundaries; a draft status until a user promotes it; and a record of the time from idea to promotion, so that the criterion "a second skill within one month" can be checked.
- **FR-21 Accounts and login** [OP-5] (proposed; replaces the shared editor and chat tokens, D-6, D-12). Only the owner creates accounts. Every user logs in with a local account and password, may change their own password, keeps a session on their devices, and every action that changes shared data is attributed to the account. Passwords are stored only as salted slow hashes; repeated failed logins are throttled.
- **FR-22 Graph app** [TK-10 reversed] (proposed; D-9, D-11). MIA shall provide a graph app, a web page in the same stack as the chat (plain HTML and JavaScript, a vendored graph library, no build step), that shows workflow graphs as nodes and edges and lets any logged-in user edit each node and edge directly as a JSON dictionary (text data only). It reads and writes the shared database through the backend, checks the graph rules (node identity, no two data nodes adjacent, no cycle, a stopping criterion on every session node) before saving, saves every edit as a new version, and shows the version history and a diff.
- **FR-23 Mood in every situation** [CT-2, EM-1, EM-2] (partly: mood from the emotion keyword and the activity; CR-1). MIA shall hold a mood at all times, including when idle, thinking, speaking, waiting in the queue, greeting a user who logs in, reporting an error and being offline, and the character shall show the expression and gesture that an editable mood map assigns to that mood; an unknown mood falls back to neutral, and the mood changes with events and settles back over time. The overall feedback score (FR-27) shifts the general mood. A voice line (FR-31) may accompany the mood.
- **FR-24 Character exchange** [CH-1, CH-2] (partly: scripts exist for the Blender route; CR-3). A user shall be able to select the character from a VRoid model in `.vrm` format and to transfer both the original files and the compiled web export between machines with scripting tools (import, build, pack, unpack); expressions and gestures defined for one model are mapped to the shape keys of another or reported as missing, never silently dropped.
- **FR-25 Persona from a file** [ME-1] (partly: `calibration.txt` is sent at every start, behaviour unmeasured; CR-5). MIA shall behave roughly as the persona file specifies: she uses the names and pronouns given there correctly and addresses every user as "master" by default unless the persona file specifies otherwise (D-14, D-16) and repeats back-story elements in fitting situations (the file today names the role of a virtual maid, MIA-chan, the form of address master, a salary in DEP and a diligent, earnest personality that is sometimes cheeky or sarcastic; it has no further back story); `calibration.txt` is one shared parameter file for all users and the baseline of the persona (D-22, D-35); every user can change it (FR-5) and a change applies to all (D-22). How well she keeps it is measured by a persona suite in Plan.
- **FR-26 Workflow specification and benchmark** [TK-2, TK-3, TK-4, EV-1] (partly: nodes and skill stages declare schemas, suites and a harness exist; a specification per workflow with criteria is new; D-15). Every workflow (skill with its pipeline) shall carry a written specification that states its **inputs and outputs** (schemas, units, allowed values, what "unknown" looks like), its **measurable acceptance criteria** (metric, threshold, number of repeats, model pin, decision rule, budgets of tokens, time and calls), a **context graph** (FR-30), and a **benchmark**: a set of test cases with labelled truth, a development part for tuning and a held-out part for decisions, and a recorded baseline. The specification is stored with the workflow in the library; the cases, suites and baselines of the benchmark are files in `eval/` (protected, in git), referenced by suite id and version, and run results are stored in the database; a workflow without a specification and a benchmark can only be a draft; every run of the harness records the versions of the workflow, the model pin and the benchmark, so that variants can be verified against the criteria and optimised against each other on the same cases. Stability across repeats is one of the measurable criteria of every workflow.
- **FR-27 Feedback and points** [BF-2, CT-2] (proposed; CR-6, D-16). Every user can give a plus or a minus on an answer, a reaction or a behaviour of the character. A vote counts in one of four categories (**answer quality, reactions, character behaviour, service**); a plus adds and a minus subtracts points in that category (the value per vote and the weight per category are settings), and MIA keeps a score per category and an overall score, over time, in the shared database, each vote with its user, time and the thing voted on. A small story tells what MIA receives for the points: the currency is named in the parameter file of FR-25 (today **DEP, Digital Electric Points, her salary**); the words are data, purely fictional, shown in the page. The overall score is shown over time and shifts MIA's general mood (FR-23); the interval over which the score is judged (one week at first) is a setting that may be changed (D-23). The scores are used to compare versions of workflows and behaviours over time; they never decide a fact (NFR-4, BF4): a minus on a factual answer opens a case for the benchmark instead of changing what MIA states.
- **FR-28 Tasks and memos** [ME-1, ME-2] (partly: an hourly time check and a `TASK:` convention in the memory; CR-7). MIA shall store tasks (text, optional due time, status, who created them) and memos (free text, who, when) as records in the shared database, and shall recite them correctly: on request and at the due time the text is read back from the records by code, word for word, never regenerated by the model; every user sees and may change all of them (CON-6).
- **FR-29 Adaptation to negative feedback** [BF-1, BF-2] (proposed; CR-8, D-16). MIA shall give each behaviour of the character that a user can vote on (a gesture, an expression, a reaction, a recurring phrase or turn of speech) an identity, and shall show a behaviour less often after each net negative vote on it; after at least 5 net negative votes it shall occur with a chance of at most 1 % per opportunity; positive votes can bring it back. On a negative vote MIA behaves shocked (a fitting expression and a short reaction). The rule applies to style and reactions, never to facts or to safety checks (BF4); any user can see and reset the counters (CON-6).
- **FR-30 Workflow context graph** [TK-5, LG-3] (proposed; a graph per run exists in code; D-17, D-21). MIA shall keep **one context graph per workflow and one context graph for the chat as a whole**: the concepts, entities, source types and relations that the workflow (or the conversation) works with, and the views that say which part of it each step sees within its token budget. The context graphs are stored in the shared database, can be adapted by any user in the graph app (every change a new version, FR-22), and are what makes a workflow traceable. A graph per run is built only for tasks that need working memory of their own, for example extending a keyword search; it is not a general mechanism.
- **FR-31 Voice lines** [VO-3, CT-7, EM-1] (partly: a clip per expression, intro sounds and attention sounds exist; most newer moods have no line yet; the shocked line is new; D-25). MIA shall speak short **voice lines** for moods and events: a greeting when a user opens the page or logs in, a line per mood or expression (for example yes, no, annoyed, surprised), an attention call such as "Hey, listen!" before she speaks on her own initiative (a task coming due, the hourly time check) with a chance that is a setting, and a shocked line on a negative vote (FR-29). A line is data, a text with an audio file, made with the TTS and the voice effect (FR-3) or supplied as a recording; every user can add, replace or remove lines (FR-5); the line is chosen by mood and event, at random among several; a mood without a line stays silent and a missing file is skipped without an error and logged. The default lines ("Hello!", "Hey!", "Listen!" and one per mood) are generated with the TTS, so that MIA needs no third-party recordings (D-26).
- **FR-32 Character variant per workflow** [CH-11, TK-8] (proposed; D-27). Every workflow can name a character variant, a choice of shown or hidden parts and colours of the character (for example another outfit), which the character wears while the workflow runs and which the chat shows as a small label; a workflow without a variant uses the variant of the chat. Variants are data that every user can create, change and select in the character editor, and a change applies to all.
- **FR-33 Workflow schedule** [TK-5, TK-9] (proposed; amendments 1 to 3, D-41, D-42, D-43). MIA shall compute from the graph of a workflow and the measured costs of its process nodes (seconds, calls and tokens from the run log; for a session node its stopping criteria times the cost of one cycle) a schedule before the run: the order, the steps that can overlap, the critical path, and an estimate of time, calls and tokens; she shows the estimate and refuses to start a run whose estimate exceeds its budget (FR-26).

### 3.2 Non-functional requirements
- **NFR-1 Accessibility and device range** (Usability) [CT-10] (built). Keyboard and screen-reader use, dark and light themes, reduced motion, widths 320 to 2560 px, current Chrome, Firefox and Safari (iOS 16+), touch targets of at least 44 px.
- **NFR-2 Small-model strategies** (Efficiency, research core) [TK-6, TK-9, RS-3] (built for lookup). Narrow steps with structured outputs and testable targets; every model input inside 50 % of the context window; code does what code can; more calls only when a target is unmet; a cheap first try of fewer than 15 model calls per question on the light model.
- **NFR-3 Untrusted input stays data** (Security) [VE-3, VE-6, RS-7] (built). Text from the web, papers, PDFs and users never acts as instruction; model-written scripts and hostile documents are processed only in an isolating sandbox; a missing sandbox means the operation is refused, never weakened.
- **NFR-4 Honest confidence** (Reliability) [RS-10, RS-11, EV-2] (partly). Confidence figures are computed by code from anchored evidence; MIA never shows a source she did not retrieve (0 invented references, 100 % of cited quotes found in their source); limits are reported with every result.
- **NFR-5 Local-first privacy** (Data handling) [C-5, CT-10, VE-6] (built). Conversations, memory, logs, accounts and models stay on the host; the only data leaving it is the text of a web or scholarly query (and an e-mail address only if configured); the page loads nothing from the internet. Inside MIA nothing is private between users (CON-6): the login page says so.
- **NFR-6 Secure access** (Security) [OP-4, OP-5] (transport built, Tailscale untried; accounts proposed). Other devices reach MIA only over HTTPS inside the home network or the tailnet; every request is authenticated by an account (FR-21); origins are checked and message rates limited per user.
- **NFR-7 Efficient on the given hardware** (Performance) [C-2, CT-9, RS-9] (partly). The first text of a chat answer appears within 10 seconds on the light model (D-34); every task runs under explicit budgets (steps, seconds, calls, tokens) and a run that exceeds one ends with what it has and says what is missing; the character runs at 30+ fps on a mid-range phone and 60 fps on desktop. Several users share one model server: waiting messages are queued, show their position and are refused only when the queue is full (length set in Plan). A chat answer has priority over a background task: a long task (a review slice) yields the model server to waiting chat messages.
- **NFR-8 Shared state in a database** (Maintainability, Reliability) [OP-7, CT-8] (proposed; was postponed, D-4, D-11). MIA shall keep her shared state (history, summaries, chat log, feedback, presets, gestures, library entries, accounts) in a PostgreSQL database in a container behind storage interfaces, so that MIA and the graph app share it; the move from files to the database is one command and reversible by export; backup and restore cover the database.
- **NFR-9 A container per node** (Deployability) [OP-1] (proposed; amendment 6, D-46). MIA shall run each of the nodes N-2 to N-5 (backend, database, evaluation and operation, graph app) as its own container under podman and serve the web frontend N-1 (static files) from the backend container; every container is startable alone and all together by the compose stack with the same configuration file (amendment 6, D-46).

### 3.3 Constraints
- **CON-1** Free and open: local models through Ollama, self-hosted search, no paid API; licence GPL-3.0-or-later.
- **CON-2** Hardware: Ryzen 9 5900X (24 threads), RX 7800 XT with **16 GB** VRAM, 62 GB RAM (measured 2026-10-24); one language model loaded at a time (`OLLAMA_MAX_LOADED_MODELS=1`). With several users the model server serves one request at a time; the others wait in a queue.
- **CON-3** Python 3.11 to 3.13 (3.12 tested); Godot 4.6.1 with GDScript only and the Compatibility renderer; the chat page in plain HTML, CSS and ES modules without build step or UI framework.
- **CON-4** The 3D character runs only on `localhost` or over HTTPS; passwords are sent only over HTTPS or on `localhost`.
- **CON-5** Remote access only inside a private network (Tailscale); no public port, never `tailscale funnel`.
- **CON-6** Trusted users only: a handful of people; all see and may edit everything (skills, workflows, presets, persona, memory); a change applies to all at once. There are no roles or per-user permissions inside MIA.
- **CON-7** One shared PostgreSQL database in a container (D-11), reachable by MIA and the graph app; MIA's state stays behind storage interfaces (`deploy/REQUIREMENTS_DB.md`).

### 3.4 Target environment and lifetime
Fedora 43 (KDE, Wayland), podman, the owner's workstation; a handful of trusted users on phones and other computers in the home network and the tailnet. The compose stack gains a database service and the graph app; backups include the database. NVIDIA and CPU-only modes exist but are not the target. Lifetime: long-term and evolving; the owner maintains it. It is not a frozen demonstrator, so deploy and freeze are about the compose stack and its backups, not about shipping a package.

## 4. Agent profile
MIA contains an app agent (prompts, skill files, pipelines, tools, verifiers on local models). The coding agent that builds MIA is a different thing and is bound by the phase rules.

### Tasks
| Task / skill | Goal | Who uses the result | Cost of a wrong result |
|---|---|---|---|
| `chat` | quick, warm answer in character, emotion keyword first | the owner, spoken aloud | low: an odd answer; medium if it invents facts about the owner |
| `lookup` (skill `research` today) | factual answer with sources and verbatim quotes | the owner, who may repeat it | medium: a wrong fact with a source attached |
| `verify_claim`, `verify_computable` | verdict on a claim (supported / refuted / unclear) | the lookup, then the owner | medium |
| `extract_claims` | claims from prose with anchored quotes | verification | medium |
| `plan_question` | sub-questions or a typed plan | lookup | low: the escalation catches bad plans |
| `summarize` / dreaming | summary of the history; target: structured memory records | MIA herself, in every later answer | **high**: a wrong summary becomes a permanent "fact" without a trace |
| expression generation | an expression preset from a description | the owner, in the editor (keep / edit / reject) | low |
| `research` (literature review, proposed) | report on how well the literature answers a question | the owner, possibly in a paper | high: invented or misread sources |
| `storytelling`, `schedule` (proposed) | see baseline TK-7 | the users | low / medium (schedule: a missed appointment) |
| tasks and memos | store and recite records word for word (FR-28) | the users | medium: a wrong or lost task |
| feedback adaptation | change how often a behaviour occurs from votes (FR-29) | all users | low, but it changes the character for everyone |

## 5. High-level architecture
### 5.1 Overview
MIA is a Python service (Flask and Socket.IO) with a speech subprocess, a model server (Ollama), a search service (SearXNG), a PostgreSQL database and an HTTPS front (proxy or Caddy), all in one compose stack on the host. Several trusted users log in with local accounts; the browser loads the chat page, the character (a Godot web export) and the graph app. Inside, thirteen subsystems: front end, web application (with the account service), graph app, conversation core (persona, feedback ledger, behaviour registry, task and memo store), task runtime, verifier, research suite, voice, observability, evaluation, learning layer (proposed), persistence (the database behind storage interfaces) and operation. The agent view shows ten model steps, five boundaries for untrusted text and the edit boundary TB-edit.

### 5.2 SysML model
`architecture.sysml` holds, in this order: shared vocabulary (status, trace), the architecture (items, ports, interfaces, `MiaSystem` with 74 leaf parts that name their code files and status), the agent view, the requirements (CON-1..7, FR-1..33, NFR-1..8), and satisfy/allocate/verification. `model/` holds the context (people, concerns, external systems) and the behaviours (chat exchange, lookup, review, consolidation, activity states). Excerpt:

```sysml
part def ExtractionStep {
    @ModelStep { schema = "claims.schema.json"; tools = ""; tokenBudget = 8192; secondBudget = 0.0;
                 pin = "MP-light"; criterion = "none: set in Plan"; }
    @TrustBoundary { boundary = "TB-web"; threats = ""; }
    port pageIn : ~PageTextPort;
}
flow of FetchedPageText from fetcher.pageOut to extractor.pageIn;
satisfy fr9 by mia;
allocate fr9 to mia.verifier.hardChecks;
```

This is a description of an existing system, so the architecture mirrors the code base (module names in `Implementation.modules`, all checked to exist). New parts are the ones with status `proposed`: review pipeline, method transfer, workflow graph generation, storytelling, the learning layer, judge calibration, structured memory.

### 5.4 Key decisions and alternatives
| Decision | Alternatives considered | Rationale |
|---|---|---|
| Chat in plain HTML/JS, character in Godot | chat inside Godot | text input, selection, keyboard and markdown are far better in the browser |
| PostgreSQL in a container holds the shared state; library entries live in the database with a file export and seed (D-11, D-13) | files as truth, SQLite as index | several users and the graph app share the state; SQLite on a shared volume is not safe |
| One shared MIA: one memory, one persona, one score for all users; all users see everything (D-4, D-5) | a memory per user | a handful of trusted users; one character everybody talks to |
| Local accounts with passwords, created by the owner (D-6, D-12) | identity provider, tailnet identity, self-registration | simplest for a handful of trusted users; no external service |
| One context graph per workflow and one for the chat; a graph per run only where a task needs one (D-21) | a graph per run as the general mechanism | traceable by one adaptable artifact per workflow; the event log stays the source of truth for what happened |
| A chat answer has priority over background work (NFR-7) | first come, first served | one model server; a long review slice must not freeze the chat |
| Votes adapt style and reactions, never facts (FR-29, FR-27) | votes train everything | approval must not become the reward for being agreeable (BF4) |
| Roles are views of one model first | separate models per role | one slot on the GPU; separate models are a measured comparison later |
| Hard checks before model styles; "unknown" allowed | model-only verification | cheap and strong first; self-correction without evidence does not help |
| Research = literature review; the old process is `lookup` | one process for both | a single question is too atomic; the review is the unit (RV3) |
| A graph app (plain HTML and JavaScript) on the database, reversing the drop of 2026-10-22 (D-9, D-11) | text tools and DOT/Mermaid export only | users edit nodes as JSON and every edit is a new version; the text tools stay for explaining runs |
| SysML kept as one HLS-level file plus supplements | one file per concern | the workflow scripts read `architecture.sysml`; context and behaviour are optional |
