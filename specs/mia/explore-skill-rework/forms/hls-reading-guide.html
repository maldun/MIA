FR-36 Skill definition [–] (proposed). MIA shall define every skill as one versioned record of an ID, a command, a workflow graph and the ID of an associated context graph. The skill file, the extension manifest and the pipeline reference of today are replaced by it, one skill at a time (FR-45).

FR-37new

before
(did not exist)
now
FR-37 Workflow graph model [–] (proposed; revises FR-7). MIA shall hold a workflow as a directed acyclic graph of three node types: data nodes (a dictionary or dataclass that can be written as JSON), transform nodes (a function of the toolbox, FR-38) and master nodes (an agent task with an acceptance criterion, FR-39). A graph carries an ID, the ID of its context graph, the ID of its testbench (FR-44) and a description. The graph rules of FR-7 (unique identity, no cycle, a stopping criterion where one is needed, data nodes connected only through processes) stay unless Plan changes them. A data node has at most one transform that writes it; several transforms may read it.

before
(did not exist)

FR-38 Toolbox and exchange of transforms [–] (proposed). MIA shall collect transforms in a toolbox, reference them by ID, and keep them in a form that can be stored and exchanged outside MIA. An imported or exchanged transform has the status untrusted until the owner marks it trusted; a node whose transform is not trusted does not run. A review process for exchanged transforms is a later goal.

FR-41new

before
(did not exist)
now
FR-41 Context graph [–] (proposed; revises FR-30). MIA shall keep context graphs as general typed directed graphs: node categories and edge types given as JSON schemas, every element an ID and a JSON entry. Every skill names exactly one context graph by its ID; different skills may name the same one, and the chat has one too. A run records the ID and version it read. A step reads the confirmed part of its context graph into its prompt within a token budget; work and reviews extend it over time. A knowledge graph is one kind of context graph. A tested or trusted skill pins the version of its context graph and a draft follows the latest; a new version of a graph marks the testbenches of the skills that name it as stale. The chat's context graph is the one of a skill record with the ID chat. Every item carries a data class, and a step reads only the classes its definition allows. The share of a step's context that may come from the context graph is a configuration value.

FR-43new

before
(did not exist)
now
FR-43 Skills window, viewer and editor [–] (proposed; revises FR-22, takes up FB-02). MIA shall show skills in a window of their own in the web interface, apart from the skills panel of FR-34 that shows runs. The window lists skills, shows and edits workflow graphs and context graphs (selecting and moving nodes, editing an element's JSON) and shows versions and a diff. Only the owner writes; other accounts read. Every edit is checked against the graph rules before it is saved as a new version. The owner promotes a version from draft to tested to trusted. Workflow graphs are drawn left to right, context graphs as a free network, both by one viewer that draws with a vendored library without a build step (vis-network, the owner's choice; a new dependency to be pinned and licence-checked in Plan). An element's JSON is edited as text and validated by the server. Proposed items of a context graph are drawn dashed and can be confirmed or rejected, with a filter by source and by skill. A graph shows the skills that use it. Two versions are compared in one overlay that colours added, removed and changed elements. On the phone graphs are view-only. Where the run events allow it at small cost, a running skill's current step is highlighted on its workflow graph.

FR-46 Skill subwindow and spoken-only chat [–] (proposed; revises FR-34 and FR-35). MIA shall give every skill a subwindow of its own in the web interface that holds everything of a run that is not spoken: status card, phases, budgets, pause, resume and stop, the full result, intermediate material, the links to files and report, and a confirmation of each answer the user gave, so that the subwindow is the history of the run. Decisions of the owner (interview.md, 2026-11-02 and 2026-11-03):
1. Increments, in this order: foundation (data structure, node types, storage, today's skills migrated), then the skills window with viewer/editor, then context graphs and their builder, then benchmarks and master-node debates.
2. Transforms can be stored outside MIA for exchange; a review process for them comes later (a later goal).
3. Until then an imported transform is stored but not runnable; a person marks it trusted.
4. The finalization criterion of a master node is a function; four kinds are predefined (deterministic check, judge or vote, person approves, budget end), more can be added; a user-added function is a transform and follows decision 3.
5. A context graph is knowledge the agent reads at run time. A knowledge graph is one kind of context graph. 7. A testbench is an eval suite plus budgets; a workflow becomes tested or trusted only when it passes.
8. Debates are built on MIA's own runner; no framework (no langgraph), no new dependency for that.
9. Today's skills are converted one by one; old and new run side by side until the converted skill passes the same suite with the same pins.
10. Every debate carries its own definition of how it runs; variants for different machines are part of it.
11. Only the owner edits skills, workflow graphs and the context graph; other accounts read.
