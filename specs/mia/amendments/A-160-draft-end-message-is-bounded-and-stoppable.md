# A-160 (DRAFT 2026-11-17, owner decisions of the same day in the first real /review): the end message of a run is bounded, can be stopped and keeps the status line until it is ready

Number: A-159 is taken (split snapshots); check A-160 against the parent's range before applying. Goal: G-V3.CHAT (follows A-156 and A-158). Nothing in this draft is applied: requirements are Draft, no code is changed for them.

## Finding (first real `/review`, 2026-11-17, run `01794952818010348-121f`, question "The impact of devops in software development", 400 works screened)
The skill returned its report at 23:25:33 local (142 KB, 35 000 tokens). The chat then showed nothing for about 15 minutes, Stop and pause had no effect, and the end message that came was cut in the middle, in text and in speech.
Evidence (data of the run, local only):
1. The end message is 14 112 characters and ends in "... Other works [Open in the Skill run view](#run=...)". REQ-CHA-052 only has the prompt ask for 1200 characters; the model ignored it, and the call (input up to 4096 tokens plus about 3500 tokens of output) hit `num_ctx` 8192, so the server stopped in the middle of a sentence. REQ-CHA-063 passes the text on uncut, so the cut text and its voice line went out as they were.
2. A message of 14 000 characters is part of the model history of the next chat turns (REQ-CHA-046): the next answer, to "is the report finished?", is cut after 80 characters. Plausible cause: the context is full (not proven; a Stop press on that call is not excluded).
3. The digest of a result of this size is about ten model calls in a row per round (REQ-CHA-050, 051, up to 5 rounds), each call with a reload of the model on the machine; no call looks at the stop flag, so Stop, and with it the user, has no way in for a quarter of an hour.
4. The status line is cleared before the digest starts (`_clear_line` before `_turn_text`), so during these minutes the chat shows nothing at all. REQ-CHA-069 only demands that the clearing comes before the end message.

5. The wait was longer than the work needs (owner, 2026-11-18: "artificially long", and the report could be downloaded from 23:25 on). The Ollama log of the container (`podman logs ollama`, UTC) shows 36 requests between 22:25:33Z (the report is stored) and 22:41:48Z (the end message), always in pairs: two requests start about 4 s apart, last almost the same time (39.78 s and 39.73 s; 1m13s and 1m13s) and each stream starts its next request when its own last one ended. So two workers digested at the same time and slowed each other; the cause is not found (the only production path to the digest is `_turn_text` in `chat_service.py`, and `ModelTurns` should allow one model call at a time, so one stream bypasses it). To be found with a failing test first: with a fake model that counts concurrent calls, the end message of a run makes each digest call once and never two at a time (TC-CHA-081); if the test is green on the fakes, the second stream is in the wiring of `web_app.py` and is looked for with a call log (thread, prompt hash) in the next real run.

Separate finding of the same run, fixed already (test first): the end message was placed below the command and above the questions, because the page sorted it by the id of the run (REQ-WFM-036, "as a new message at the end of the chat"). Test `tests/js/end-message-placement.test.mjs` (TC-WFM-036), change in `chat-model.js` and `chat.js`.

## Owner's decisions (2026-11-17)
- The end message is bounded: a cap on the output of a digest call and one more call that shortens a too long summary (the cut must not happen; REQ-CHA-063 stays: the code itself never cuts the text).
- The end message comes as a new message at the end (done).
- **A (2026-11-18): Stop during the end message gives the plain sentence** `The run is done.` with the link; no further model call.
- **C (2026-11-18): the report stays in the file and the Skill run view as it is; the digest reads the short result of the skill**, not the report (new REQ-WFM-142 below).
- **B (2026-11-18): no limit is proposed.** The 15 minutes were only the time this run took. With C the digest is normally one call, so no time budget is planned; the number of calls and seconds of the end message are measured in the next real runs.

## Changes
1. **New REQ-CHA-073, output of a digest call** (group ST, Must, Test): the Chat agent shall ask the model server for at most 1024 tokens in each model call of SkillDigestStep. Rationale: the input of a call is limited to 4096 tokens (REQ-CHA-050); with 1024 tokens of output a call stays inside `num_ctx` 8192 with the system prompt and the persona, so the server never ends a text at the context limit. Acceptance criterion (AC-39): with a fake model that records the options of each call, a summary of a long result makes only calls with `num_predict` 1024 (exact). Parent: REQ-BE-078.
2. **New REQ-CHA-074, a too long summary is asked again once** (group ST, Must, Test): when the text of the last call of SkillDigestStep is longer than 1200 characters, the Chat agent shall ask the step once more to shorten that text to at most 1200 characters and pass on the text of the second call. Rationale: REQ-CHA-052 only asks, a 12B model does not always comply; the second call gets the short text (at most 1024 tokens) and costs seconds; the code still never cuts (REQ-CHA-063 unchanged). Acceptance criterion (AC-39): with scripted replies (a) a first reply of 800 characters makes one call, (b) a first reply of 3000 and a second of 900 characters makes two calls and the chat gets the 900 characters, (c) a first reply of 3000 and a second of 2500 characters makes two calls (no third) and the chat gets the 2500 characters unchanged (exact). Parent: REQ-BE-078, refines REQ-WFM-036.
3. **New REQ-CHA-075, Stop ends the end message** (group ST, Must, Test; decision A of the owner): when the user stops while the end message of a run is made, the Chat agent shall make no further model call for it and end the run with the plain sentence of its outcome and the link. Rationale: Stop must work at every point of a run, also in the minutes after its skill returned. Acceptance criterion (AC-39): with a long result of ten pieces and a stop during the first piece call, no further model call is made, the end message is the plain sentence `The run is done.` with the link (outcome done, the result is stored) and the chat model history holds no digest text (exact). Parent: REQ-BE-078, REQ-CHA-004.
4. **REQ-CHA-069 clarified** (status stays Verified-after-approval, History line added): the clearing of the status line is sent when the text of the end message is ready, before the message is added, whether or not a line was shown; until then the line shows the phase the run was in. Acceptance criterion adds: with a digest that takes a scripted time, the line is not cleared before the digest has returned (exact order: line, digest call, clearing, message). TC-CHA-074 stays as it is and is complemented by TC-CHA-080.
5. **New REQ-WFM-142, the result of the review is short** (Workflow management, subject TaskRuntime, group ST, Must, Test; decision C of the owner): the Workflow management shall deliver the review with a result that holds the question, the cut-off, the way the run ended, the summary (coverage, what was found, gaps) and the flow count, and no list of works; the full report stays in the run report, the record of the report and the files, unchanged. Rationale: the end message is worded from the result (REQ-WFM-036, IF-201 `done`); a result with every screened work was 142 KB for 400 works and made about ten digest calls and a cut text; the report is read in the Skill run view and the files, as before. Acceptance criterion (AC-39): with a scripted review of 400 screened works the returned result holds the question, the summary and the flow line, none of the sections `Included`, `Maybe` and `Excluded although closely related`, and is shorter than 8000 characters; the run report and the `.md` file are the same texts as before (exact). Parent: REQ-BE-053, refines REQ-WFM-018 and REQ-WFM-139. Code: `extensions/review/review_chat.py` (`run_review` returns the short text, `format_report` is unchanged and still goes to `run_report` and `files`); the version of the review skill goes up. Check against the contracts: IF-201 `done` says "the full result" and the IF-101 record field `result`: the text of the contract is reworded to "the result of the skill" in the same amendment; the Skill run view shows the short result in its result block and the report in its report part (REQ-CLV-048), to be checked in the first real run.
6. **Eval material** (agent-app): the prompt of the shortening call is a new task text of the digest step, so the version of SkillDigestStep goes up; the bad output (14 112 characters for a 142 KB report) is proposed as an eval case of the suite `skill_turns` in the log, labelled by a person (never by the agent); the dev eval of the criteria of REQ-CHA-052/053 is run again after the change (feedback, not verification).
